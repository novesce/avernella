# Sync: การรับความเปลี่ยนแปลง

[สารบัญ](README.md) · ก่อนหน้า: [การลงชื่อเข้าใช้](sign-in.md) · ถัดไป: [ข้อความ](messaging.md)

LINE ไม่ได้ผลักข้อความมาที่เดสก์ท็อปผ่านซ็อกเก็ต แต่เดสก์ท็อปจะถามว่า "มีอะไรเปลี่ยนตั้งแต่ revision N บ้าง?" แล้ว LINE ถือคำถามนั้นค้างไว้จนกว่าจะมีคำตอบ หน้านี้อธิบายลูปนี้และสิ่งที่ไคลเอนต์ทำกับคำตอบ

## Operation และ revision

LINE อธิบายความเปลี่ยนแปลงทุกอย่างของบัญชีเป็น **operation** เช่น ได้รับข้อความ ส่งข้อความจากอุปกรณ์อื่น โปรไฟล์เปลี่ยน มีเพื่อนใหม่ มีสายเรียกเข้า operation มีหมายเลข **revision** ที่เพิ่มขึ้นเท่านั้น ไคลเอนต์เก็บตัวชี้ตำแหน่ง (cursor) คือ revision สูงสุดที่นำไปใช้แล้ว และขอทุกอย่างที่มาหลังจากนั้น

struct ของ Operation ตามที่ไคลเอนต์อ่าน

| ฟิลด์ | ความหมาย |
| ----- | -------- |
| 1 | revision (i64) |
| 2 | เวลาที่สร้าง เป็นมิลลิวินาทีแบบ Unix |
| 3 | ชนิด (หมายเลข OpType ดูตารางด้านล่าง) |
| 10, 11, 12 | param1, param2, param3: สตริงที่ความหมายขึ้นกับชนิด สำหรับ operation ด้านโปรไฟล์ param1 คือตัวบุคคล สำหรับการโทรเป็นผู้โทร โทเค็น และคำอธิบายแบบ JSON |
| 20 | Message สำหรับ operation ด้านข้อความ |

## ตัวชี้ตำแหน่ง

[`talk_sync.c`](../../src/talk_sync.c) เก็บตัวชี้ตำแหน่งไว้ใน `struct line_talk_sync`

| สมาชิก | ความหมาย |
| ------ | -------- |
| `revision` | revision ของ operation ล่าสุดที่นำไปใช้แล้ว เป็น -1 ก่อนรู้จุดเริ่ม |
| `global_revision`, `individual_revision` | ตัวชี้ตำแหน่งอีกสองตัวที่ LINE ส่งมาและคาดว่าจะได้กลับไป |
| `partial` | หมวดเป้าหมายของ partial resync ที่ค้างอยู่ หรือ `NULL` |
| `more` | LINE บอกว่ายังมี operation รออยู่อีก |

`line_talk_sync_request()` สร้างอาร์กิวเมนต์ของ `sync`: `{1: {1: revision, 2: 100 (จำนวน), 3: global revision, 4: individual revision, 6: หมวดของ partial (map<i32, i64>)}}`

คำตอบเป็น union ที่มีแค่หนึ่งในสามแขน `line_talk_sync_apply()` จัดการแต่ละแขน

| แขน | เนื้อหา | ไคลเอนต์ทำอะไร |
| --- | ------- | -------------- |
| 1, operations | ฟิลด์ 1 คือรายการ operation, 2 คือ "ยังมีอีก", 3 และ 4 คืออีเวนต์ global และ individual (ฟิลด์ 2 ของแต่ละตัวคือตัวชี้ตำแหน่งใหม่) | เรียง operation ตาม revision ถ้า LINE ยังไม่เรียง นำตัวที่ใหม่กว่าตัวชี้ตำแหน่งไปใช้ตามลำดับ ขยับตัวชี้ตำแหน่ง และรับค่า global กับ individual ที่ใหญ่กว่า ถ้ามี "ยังมีอีก" และมีความคืบหน้า จะถามต่อทันที |
| 2, full resync | ฟิลด์ 2 คือ revision ถัดไป | กระโดดตัวชี้ตำแหน่งไปข้างหน้าและตั้ง `reload` UI จะโหลดรายการแชตและแชตที่เปิดอยู่ใหม่ |
| 3, partial resync | ฟิลด์ 1 คือ map ของหมวดกับ revision | เก็บหมวดไว้ ตั้ง `reload` เมื่อหมวดเปลี่ยนครั้งแรก และถามต่อพร้อมเติมฟิลด์ 6 จนกว่า LINE จะกลับมาตอบเป็น operation |

คำตอบแบบอื่น (มีมากกว่าหนึ่งแขน revision ติดลบ รายการผิดรูป) จะถูกปฏิเสธโดยไม่เปลี่ยนอะไร

## Long poll

[`live_sync.c`](../../src/live_sync.c) รันเธรด `line-sync` ซึ่งมีสำเนาตัวชี้ตำแหน่งกับ access token เป็นของตัวเอง และมีการเชื่อมต่อ HTTPS ของตัวเอง

แต่ละรอบ

1. เรียก `sync` บน `/SYNC4` พร้อม `x-lst: 50000` LINE จึงถือคำขอค้างไว้ได้ 50 วินาที
2. LINE ตอบทันทีที่มีอะไรเกิดขึ้น หรือหลังราว 50 วินาทีถ้าไม่มีอะไร
3. เธรดนำคำตอบไปใช้กับตัวชี้ตำแหน่งของตัวเอง เก็บ operation และเพิ่มเข้าชุดข้อมูลภายใต้ mutex และบันทึก access token ที่ถูกหมุนเวียนถ้าคำตอบมีมาด้วย
4. ถ้ามีอะไรใหม่ (operation, reload, โทเค็นที่ถูกหมุนเวียน หรือการฟื้นจากความล้มเหลว) จะเขียนลง **eventfd** ของตัวเอง ซึ่งปลุก `poll()` ของ worker
5. จังหวะ
   - หลังล้มเหลว รอ `max(Retry-After, 1, 2, 4… สูงสุด 32 วินาที)`
   - หลังคำตอบว่างที่กลับมาในเวลาไม่ถึง 0.8 วินาที (LINE ไม่ได้ถือค้างไว้) จะรอให้ครบหนึ่งวินาที เซิร์ฟเวอร์ที่ไม่ทำ long poll จึงถูกถามได้ไม่เกินวินาทีละครั้ง
   - นอกนั้นเริ่มรอบถัดไปทันที

การหมดเวลา 50 วินาทีตอนว่างไม่นับเป็นความล้มเหลว ข้อผิดพลาดอื่นเพิ่ม `failures` (สูงสุด 6) และชุดข้อมูลจะรายงาน `failing` ตลอดที่ยังล้มเหลว

worker รับชุดข้อมูลใน `live_operations()` ของ [`main.c`](../../src/main.c) ด้วย `line_live_sync_take()` เมื่อ worker ต่ออายุหรือได้ access token ใหม่ จะส่งให้เธรดด้วย `line_live_sync_set_access()` การหยุดเธรด (`line_live_sync_stop()`) คือการปล่อยมันไป มันจะจบเองหลังคำขอปัจจุบันกลับมา

เมื่อตั้ง `LINE_DEBUG_SYNC=1` แต่ละรอบจะพิมพ์ `line-sync reply after <ms> ms, <n> operations`

## จุดเริ่มและการตรวจสำรอง

long poll เริ่มไม่ได้จนกว่าไคลเอนต์จะรู้ว่า "ตอนนี้" อยู่ตรงไหน ไม่เช่นนั้นการลงชื่อเข้าใช้ครั้งแรกจะเล่นประวัติทั้งหมดของบัญชีซ้ำ รวมถึงคำเชิญโทรเก่า ๆ ด้วย `sync_revision()` ใน `main.c` ซึ่งทำงานตามตัวจับเวลาบำรุงรักษาแบบครั้งเดียวของ worker จัดการเรื่องนี้

1. **จุดเริ่ม** ครั้งแรกจะเรียก `getLastOpRevision` บน `/S4` แล้วตั้งตัวชี้ตำแหน่งเป็นค่าที่ได้ ไม่มีอะไรก่อนหน้านั้นถูกนำมาใช้ จากนั้นจึงเริ่มเธรด long poll
2. **ระหว่างที่ long poll ทำงานปกติ** ตัวจับเวลาทำงานทุก 2 วินาทีเพื่องานบำรุงรักษาเท่านั้น ได้แก่ หมดอายุคำเชิญโทรที่ไม่ได้รับ (`line_voice_tick()`) ต่ออายุโทเค็น (`maintain_tokens()`) และบันทึกโทเค็นที่ถูกหมุนเวียน
3. **ระหว่างที่ long poll ล้มเหลว** ตัวจับเวลาถอยมาใช้การตรวจ revision แบบประหยัด ถ้า `getLastOpRevision` สูงกว่าตัวชี้ตำแหน่ง จะเรียก `sync` แบบธรรมดาหนึ่งครั้ง (poll 2 วินาที, `poll_call_operations()`) เพื่อรับ operation แล้วส่ง `changed` ไปที่ UI ตรวจทุกวินาทีขณะหน้าต่างได้โฟกัสหรือยังมีให้ดึงอีก นอกนั้นทุก 3 วินาที
4. **เมื่อเครือข่ายล่ม** จะแสดง "Automatic chat refresh is unavailable" หนึ่งครั้ง แล้วเว้นระยะ 3, 6, 12, 24 แล้วทุก 30 วินาที
5. **เมื่อ LINE ปฏิเสธเซสชัน** จะลืมเซสชันแล้วส่ง `signed_out`

คำขอ `foreground` จาก UI บอก worker ว่าหน้าต่างได้โฟกัสหรือไม่ เมื่อได้โฟกัส worker จะตั้งตัวจับเวลาใหม่ให้ตรวจเร็วขึ้น

## การนำ operation ไปใช้

สำหรับ operation แต่ละตัวในชุด `live_operations()` จะ

1. เรียก `apply_operation()` ซึ่งส่ง operation ให้ `line_profile_operation()` (ใน [`messaging.c`](../../src/messaging.c) ล้างแคชชื่อที่แสดงเมื่อโปรไฟล์หรือแชตเปลี่ยน) และ `line_voice_operation()` (ใน [`call.c`](../../src/call.c) ตรวจหาสายเรียกเข้า)
2. ลอง `message_operation()` สำหรับ operation ด้านข้อความ
3. ถ้าไม่ใช่ ลอง `social_operation()` สำหรับ operation ด้านเพื่อนและโปรไฟล์ (ไม่เกิน `LIVE_CARD_LIMIT` ต่อชุด)
4. ถ้าไม่ใช่อีก ก็จดไว้ว่ามี "อย่างอื่น" เปลี่ยน

จากนั้น

- ถ้ามีอย่างอื่นเปลี่ยน หรือมีการขอ resync จะส่งอีเวนต์ `changed` หนึ่งครั้ง แล้ว UI โหลดรายการแชตและแชตที่เปิดอยู่ใหม่
- ถ้าไม่ใช่ แต่มีข้อความเข้ามาในแชตที่เปิดอยู่ จะเรียก `revalidate_history()` เพื่อดึงหน้าล่าสุดของแชตนั้นแล้วส่งอีเวนต์ `history`

### Operation ด้านข้อความ

`message_operation()` จัดการ SEND_MESSAGE (25 ส่งจากบัญชีนี้ ไม่ว่าจากอุปกรณ์ไหน) และ RECEIVE_MESSAGE (26) จาก Message ในฟิลด์ 20 มันหาว่าเป็นแชตไหน: ถ้าเป็นข้อความตัวต่อตัว (`toType` 0, Message ฟิลด์ 3) ที่ได้รับจากคนอื่น แชตคือ MID ของผู้ส่ง ถ้าไม่ใช่ แชตคือผู้รับ (ฟิลด์ 2) ซึ่งเป็นกลุ่ม ห้อง หรือคนที่คุณเขียนถึง จากนั้นจะ

- ส่งอีเวนต์ `chat_message` พร้อมแชต รหัสข้อความ เวลา และบอกว่าเป็นของคุณหรือไม่ UI จึงย้ายแชตนั้นขึ้นบนสุดได้โดยไม่ต้องโหลดใหม่
- บันทึกรหัสข้อความล่าสุดของแต่ละแชตใน `unread_heads` โดยไม่ถอยหลังเลย แม้ LINE จะส่ง operation ซ้ำ
- ทำเครื่องหมายว่าแคชประวัติของแชตนั้นล้าสมัย หรือทิ้งแคชถ้าแชตนั้นไม่ได้เปิดอยู่

### Operation ด้านเพื่อนและโปรไฟล์

`social_operation()` แปลง operation เหล่านี้เป็นอีเวนต์เล็ก ๆ ที่แก้ UI ตรงจุด เหมือนแอปแชตที่อัปเดตผู้ใช้คนเดียวแทนการโหลดใหม่ทั้งหมด

| OpType | ชื่อ | อีเวนต์ที่ส่ง |
| ------ | ---- | ------------- |
| 1 | UPDATE_PROFILE (ตัวคุณเอง จากอุปกรณ์ไหนก็ได้) | `self` พร้อมโปรไฟล์ล่าสุดของคุณ |
| 5 | NOTIFIED_ADD_CONTACT (มีคนเพิ่มคุณ) | `friend_added` พร้อมการ์ดของเขา |
| 88 | NOTIFIED_FRIEND_REQUEST | `friend_request` |
| 2, 4, 6, 7, 49, 63, 78, 141 | NOTIFIED_UPDATE_PROFILE, ADD_CONTACT, BLOCK_CONTACT, UNBLOCK_CONTACT, UPDATE_CONTACT, FRIEND_REQUEST_ACCEPTED, NOTIFIED_BUDDY_UPDATE_PROFILE, NOTIFIED_UPDATE_PROFILE_CONTENT | `contact` พร้อมการ์ดของคนนั้น |

การ์ดดึงด้วย `line_friend_card()` (ดู [เพื่อน](social.md)) `ui_profile_packet()` ของ UI อัปเดตแถวแชต การ์ดโปรไฟล์ที่เปิดอยู่ และ Inbox

## ชนิด operation ที่ไคลเอนต์จัดการ

| OpType | ความหมาย | จัดการโดย |
| ------ | -------- | --------- |
| 1 | โปรไฟล์ของคุณเปลี่ยน | `social_operation()`, `line_profile_operation()` |
| 2 | โปรไฟล์ของผู้ติดต่อเปลี่ยน | ทั้งสอง |
| 4 | คุณเพิ่มผู้ติดต่อ | `social_operation()` |
| 5 | มีคนเพิ่มคุณ | `social_operation()` |
| 6, 7 | บล็อกหรือเลิกบล็อก | `social_operation()` |
| 10, 11, 121, 122, 150 | กลุ่มและแชตเปลี่ยน | `line_profile_operation()` ล้างแคชชื่อ operation นี้นับเป็น "อย่างอื่น" รายการแชตจึงโหลดใหม่ |
| 25 | คุณส่งข้อความ (อุปกรณ์ไหนก็ได้) | `message_operation()` |
| 26 | คุณได้รับข้อความ | `message_operation()` |
| 49 | ผู้ติดต่อถูกอัปเดต | ทั้งสอง |
| 50 | คำเชิญโทรเข้า | `line_voice_operation()` ดู [การโทร](calls.md) |
| 51 | คำเชิญโทรถูกยกเลิก | `line_voice_operation()` |
| 63 | คำขอเป็นเพื่อนได้รับการยอมรับ | `social_operation()` |
| 78 | โปรไฟล์ของบัญชีทางการเปลี่ยน | ทั้งสอง |
| 88 | มีคำขอเป็นเพื่อนเข้ามา | `social_operation()` |
| 141 | เนื้อหาโปรไฟล์เปลี่ยน | ทั้งสอง |

operation ชนิดอื่นทำให้ UI โหลดรายการแชตและแชตที่เปิดอยู่ใหม่ ซึ่งถูกต้องเสมอ แค่ช้ากว่า ชนิด operation ใหม่จึงปล่อยไว้ไม่จัดการก่อนได้อย่างปลอดภัย

## การแจ้งอ่านและจำนวนที่ยังไม่อ่าน

จำนวนที่ยังไม่อ่านมาจากรายการแชต (`getMessageBoxes` ส่งจำนวนที่ยังไม่อ่านของแต่ละแชตมา ดู [ข้อความ](messaging.md)) UI ปรับค่าในเครื่องเมื่ออีเวนต์ `chat_message` มาถึง และทำเครื่องหมายว่าอ่านแชตแล้วด้วย `markRead` เมื่อคุณเห็นข้อความล่าสุดจริง ๆ (ดู [ส่วนติดต่อผู้ใช้](ui.md)) `markRead` เรียก `sendChatChecked` ซึ่งอธิบายไว้ใน [ข้อความ](messaging.md)
