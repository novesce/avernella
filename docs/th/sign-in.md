# การลงชื่อเข้าใช้และเซสชันที่บันทึกไว้

[สารบัญ](README.md) · ก่อนหน้า: [พื้นฐานโปรโตคอล](protocol-basics.md) · ถัดไป: [Sync](sync.md)

เดสก์ท็อปคือ *อุปกรณ์รอง* ของบัญชี LINE การลงชื่อเข้าใช้ต้องได้ของสามอย่าง

1. **access token** (และ **refresh token** ไว้ต่ออายุ)
2. **MID** ของบัญชี
3. **key chain ของ Letter Sealing** ของบัญชี ซึ่งโทรศัพท์เข้ารหัสส่งให้เดสก์ท็อปเครื่องนี้ เดสก์ท็อปจึงอ่านและส่งข้อความที่เข้ารหัสได้

Avernella ได้ของเหล่านี้มาได้สองวิธี คือสแกน QR code และใช้อีเมลกับรหัสผ่านพร้อมรหัสยืนยัน ทั้งสองวิธีจบด้วยเซสชันแบบเดียวกันที่บันทึกลงดิสก์

## ลำดับการทำงานในแอป

1. ผู้ใช้เลือกวิธีลงชื่อเข้าใช้บนหน้าลงชื่อเข้าใช้ `login()` ใน [`ui.c`](../../src/ui.c) เริ่ม worker (`--worker` สำหรับ QR และ `--worker-password` สำหรับอีเมล ดู [สถาปัตยกรรม](architecture.md)) แล้วส่ง `login`
2. `login()` ของ worker ใน [`main.c`](../../src/main.c) เปิดไดเรกทอรีเซสชัน (`line_store_open()`) ถ้ายังไม่มีเซสชันบันทึกไว้ จะรัน `pair_worker()` ซึ่งเรียก `line_pair()` (QR) หรือ `line_password_login()` (อีเมล)
3. ระหว่างจับคู่ worker ส่งอีเวนต์ `qr` และ `pin` และ UI แสดงรหัส
4. หลังจับคู่ worker บันทึกเซสชัน (`line_store_save()`) ถ้าบันทึกไม่สำเร็จ จะออกจากระบบเซสชันใหม่ทันทีด้วย `logoutV2` เพราะโทรศัพท์อนุมัติอุปกรณ์ไปแล้วแต่เดสก์ท็อปเก็บไว้ไม่ได้
5. worker เรียก `getProfile` บน `/S4` เพื่อตรวจเซสชันและรู้ชื่อผู้ใช้ (ฟิลด์ 20) MID (ฟิลด์ 1) และพาธรูป (ฟิลด์ 33) ถ้า MID ไม่ตรงกับที่บันทึกไว้ เซสชันจะถูกทิ้ง ("The account changed")
6. ตอบกลับเป็น `{name, selfId, capabilities}` อ็อบเจกต์ capabilities บอก UI ว่าจะเปิดฟีเจอร์ไหน (รูป ไฟล์ การโทร วิดีโอคอล ฯลฯ)
7. worker ตั้งตัวจับเวลาบำรุงรักษา ซึ่งจะตั้งจุดเริ่มของ sync (ดู [Sync](sync.md))

เมื่อมีเซสชันบันทึกไว้แล้ว UI จะเรียก `login(TRUE)` ตอนเปิดแอป และขั้นที่ 2 จะข้ามการจับคู่

## การจับคู่ด้วย QR code

อยู่ใน `pair_with_key()` ของ [`pair.c`](../../src/pair.c) ทุกการเรียกเป็น Thrift แบบ Compact บน `/acct/lgn/sq/v1` ยกเว้นการรอ ซึ่งเป็น long poll บน `/acct/lp/lgn/sq/v1`

1. **สร้างกุญแจ** `line_pair()` สร้างคู่กุญแจ X25519 ด้วย OpenSSL ครึ่งที่เป็นกุญแจส่วนตัวไม่เคยออกจากหน่วยความจำ และถูกล้างด้วย `OPENSSL_cleanse` ตอนจบ
2. **สร้างเซสชัน** `createSession()` ไม่มีอาร์กิวเมนต์ ฟิลด์ 1 ของคำตอบคือรหัสเซสชันการจับคู่
3. **ขอลิงก์ QR** `createQrCodeForSecure({1: {1: session}})` ฟิลด์ 1 ของคำตอบคือลิงก์ `line://` หรือ `https://line.me/` ฟิลด์ 2 คือจำนวนรอบการรอ ฟิลด์ 3 คือวินาทีต่อรอบ และฟิลด์ 4 คือ nonce
4. **เติมกุญแจเข้าไปในลิงก์** ไคลเอนต์ต่อท้ายลิงก์ด้วย `secret=<กุญแจสาธารณะแบบ base64 ที่ escape สำหรับ URL>&e2eeVersion=1` แล้วส่งเป็นอีเวนต์ `qr` URL นี้ *คือ* QR code ที่โทรศัพท์สแกน และเป็นวิธีที่โทรศัพท์รู้กุญแจสาธารณะของเดสก์ท็อป
5. **รอการสแกน** `poll_approval()` เรียก `checkQrCodeVerified` บนพาธ long poll โดยใช้รหัสเซสชันการจับคู่เป็นเฮดเดอร์ `x-line-access` และตั้ง `x-lst` เป็นวินาทีต่อรอบ แต่ละรอบจะสำเร็จหรือหมดเวลา (`LINE_TIMEOUT`) จนครบจำนวนรอบ (ไม่เกิน 12 รอบ รอบละไม่เกิน 120 วินาที ซึ่งเป็นค่าเริ่มต้นของ LINE สำหรับ Android เองใน `dc5.p`) รอบที่ LINE จบก่อนเวลา เช่น ตอบ 408, 410 หรือ 504 ทันที จะยังรอจนครบความยาวของรอบก่อน poll ครั้งถัดไป คำตอบที่มาเร็วจึงไม่กลายเป็นการวนถามรัว ๆ ถ้าครบรอบแล้วยังไม่สำเร็จจะได้ "The QR code expired"
6. **ตรวจว่าต้องใช้ PIN ไหม** เรียก `verifyCertificate` ด้วยอาร์กิวเมนต์เดิม การจับคู่ใหม่ไม่มีใบรับรองอุปกรณ์ LINE จึงมักตอบรหัส 1 หรือ 2 จากนั้น
   - `createPinCode` คืน PIN 4 ถึง 12 หลักในฟิลด์ 1 ไคลเอนต์ส่งอีเวนต์ `pin` แล้วผู้ใช้พิมพ์ PIN บนโทรศัพท์
   - `poll_approval()` รออีกครั้งด้วย `checkPinCodeVerified`
7. **เข้าสู่ระบบ** `qrCodeLoginV2ForSecure` โดยขยาย struct คำขอเป็น `{1: session, 2: "Avernella", 3: "Avernella", 4: true, 5: nonce}` ฟิลด์ 2 และ 3 คือชื่อระบบและชื่อรุ่นที่แสดงเป็นชื่ออุปกรณ์ที่เชื่อมบนโทรศัพท์
8. **อ่านผลลัพธ์**
   - ฟิลด์ 3 คือ `TokenV3IssueResult`: access token ในฟิลด์ 1, refresh token ใน 2, `durationUntilRefreshInSec` ใน 3 และ `tokenIssueTimeEpochSec` ใน 6 `line_schedule_refresh()` บันทึกเวลาต่ออายุ
   - ฟิลด์ 10 (หรือรูปแบบเก่า: `e2eeInfo` ในฟิลด์ 6 หรือตัวฟิลด์ 6 เอง) คือข้อมูล Letter Sealing: `encryptedKeyChain`, `publicKey` (กุญแจสาธารณะ X25519 ของโทรศัพท์), `keyId` (รุ่นที่ใช้งานอยู่) และ `hashKeyChain`
9. **นำเข้ากุญแจ** `line_import_keys()` ใน [`sealing.c`](../../src/sealing.c) คำนวณความลับร่วมจากกุญแจส่วนตัวของเดสก์ท็อปกับกุญแจสาธารณะของโทรศัพท์ ตรวจ MAC ของ key chain ถอดรหัส แล้วตรวจคู่กุญแจทุกคู่ (ดู [Letter Sealing](letter-sealing.md)) ถ้ามีอะไรผิดพลาด ไคลเอนต์จะเรียก `logoutV2` ด้วยโทเค็นใหม่เพื่อปล่อยเซสชันที่ทำค้างไว้ แล้วรายงานข้อผิดพลาด

MID ไม่ได้อยู่ในคำตอบของการจับคู่ แต่ได้จาก `getProfile` หลังจากนั้น

## อีเมลและรหัสผ่าน

อยู่ใน [`password_login.c`](../../src/password_login.c) endpoint เหล่านี้ใช้ **Thrift แบบ Binary** ไม่ใช่ Compact (ดู [พื้นฐานโปรโตคอล](protocol-basics.md))

1. **รับข้อมูลยืนยันตัวตน** worker อ่าน `struct line_credentials` หนึ่งชุด (อีเมลและรหัสผ่าน ยาวไม่เกิน 255 ไบต์ต่อช่อง) จาก fd 3 แล้วปิดและล้างข้อมูล (`pair_worker()` ใน `main.c`)
2. **ขอกุญแจ RSA ของ LINE** `getRSAKeyInfo({1: {2: 0}})` บน `/api/v3/TalkService.do` คำตอบ: ฟิลด์ 1 คือรหัสกุญแจ ฟิลด์ 2 คือ modulus ของ RSA แบบเลขฐานสิบหก ฟิลด์ 3 คือ exponent แบบเลขฐานสิบหก ฟิลด์ 4 คือ session key
3. **เข้ารหัสข้อมูลยืนยันตัวตน** plaintext คือสตริงสามตัวที่มีความยาวนำหน้า `len(session) session len(email) email len(password) password` ความยาวแต่ละตัวยาวหนึ่งไบต์ เข้ารหัสด้วย RSA padding แบบ PKCS#1 v1.5 (`encrypt()`) แล้วแปลงเป็นเลขฐานสิบหก modulus ต้องยาวอย่างน้อย 1024 บิต plaintext และรหัสผ่านถูกล้างทิ้ง
4. **สร้างกุญแจยืนยัน** `make_pairing_key()` สร้างคู่กุญแจ X25519 และ PIN หกหลักแบบสุ่ม กุญแจสาธารณะของเดสก์ท็อปถูกเข้ารหัสด้วย AES-256-ECB ภายใต้ SHA-256 ของ PIN (`make_pin_secret()`) เมื่อผู้ใช้พิมพ์ PIN บนโทรศัพท์ โทรศัพท์จึงกู้กุญแจสาธารณะของเดสก์ท็อปได้
5. **`loginV2` ครั้งแรก** บน `/api/v3p/rs` ด้วยฟิลด์ 2 ของคำขอ

   | ฟิลด์ | ค่า |
   | ----- | --- |
   | 1 | 2 (ชนิดการเข้าสู่ระบบ: ID credential พร้อม E2EE) |
   | 2 | 1 (ผู้ให้บริการตัวตน: LINE) |
   | 3 | รหัสกุญแจ RSA |
   | 4 | ข้อมูลยืนยันตัวตนที่เข้ารหัสแล้ว (ฐานสิบหก) |
   | 5 | true (คงการเข้าสู่ระบบไว้) |
   | 6 | "" (ตำแหน่งการเข้าถึง) |
   | 7 | "Avernella" (ชื่อระบบ) |
   | 10 | กุญแจสาธารณะของเดสก์ท็อปที่เข้ารหัสแล้ว (32 ไบต์) |
   | 11 | 1 (เวอร์ชัน E2EE) |
   | 12 | "Avernella" (ชื่อรุ่น) |

   รหัส 18, 19, 21 และ 23 หมายถึงข้อมูลยืนยันตัวตนผิด ถ้า LINE ออกโทเค็นให้ทันที (ฟิลด์ 9) โดยไม่มี verifier ไคลเอนต์จะออกจากระบบเซสชันนั้นอีกครั้ง เพราะเซสชันแบบนั้นไม่มีกุญแจเข้ารหัส ถ้าฟิลด์ 5 เป็น 4 แปลว่า LINE ต้องการวิธียืนยันอื่น ผู้ใช้จะถูกแนะนำให้ใช้ QR code แทน
6. **แสดง PIN แล้วรอ** ฟิลด์ 3 ของคำตอบคือ **verifier** ไคลเอนต์ส่งอีเวนต์ `pin` พร้อมตัวเลขหกหลัก แล้ว `line_auth_wait()` ทำ JSON GET บน `/LF1` โดยใช้ verifier เป็น `x-line-access` รอได้นานถึง 180 วินาที จนกว่าผู้ใช้จะกรอก PIN บนโทรศัพท์
7. **นำเข้ากุญแจ** `result.metadata` ของการอนุมัติมีฟิลด์ key chain แบบเดียวกับการจับคู่ด้วย QR `line_import_login_keys()` นำเข้ากุญแจ และคืน **proof** ขนาด 16 ไบต์ ซึ่งคือ MAC ของ key chain เพื่อแสดงให้ LINE เห็นว่าอุปกรณ์นี้ถอดรหัส chain ได้จริง
8. **ยืนยัน** `confirmE2EELogin({1: verifier, 2: proof})` คืน verifier ตัวใหม่เป็นสตริง
9. **`loginV2` ครั้งที่สอง** โดยเปลี่ยนฟิลด์ 1 เป็น 1 และตั้งฟิลด์ 9 เป็น verifier ตัวนั้น ฟิลด์ 9 ของคำตอบมีโทเค็น (1 access, 2 refresh, 3 ระยะเวลา, 6 เวลาออก) และฟิลด์ 10 คือ MID

### การลงชื่อเข้าใช้ที่ล้มเหลวและช่วงพัก

การลงชื่อเข้าใช้ด้วยอีเมลไม่ลองใหม่เองอัตโนมัติ เมื่อถูกปฏิเสธจะกลับไปที่แบบฟอร์มและรอให้ผู้ใช้กดลงชื่อเข้าใช้อีกครั้งเท่านั้น UI เก็บช่วงพักข้าม worker ที่ถูกสร้างใหม่สำหรับแต่ละครั้ง:

- คำตอบ 429 หรือ 503 ส่งจำนวนวินาที `retryAfter` ที่เหลือกลับมาที่หน้าต่าง การลงชื่อเข้าใช้จะใช้ไม่ได้จนกว่าช่วงพักจะหมด และตัวนับถอยหลังที่มองเห็นจะอัปเดตวินาทีละครั้ง
- การปฏิเสธอีเมลหรือรหัสผ่านสองครั้งแรกไม่มีช่วงพักเพิ่ม การปฏิเสธครั้งต่อ ๆ ไปต้องรอ 10 วินาที แล้ว 30 วินาที แล้ว 2 นาทีระหว่างครั้ง การลงชื่อเข้าใช้สำเร็จจะล้างจำนวนนี้ ช่วงเวลาเหล่านี้เป็นการพักอย่างระมัดระวังในเครื่อง ไม่ใช่ขีดจำกัดที่ LINE เผยแพร่
- รหัส 44 อธิบายวิธีเปิด **Allow login** บนโทรศัพท์ รหัส 16 แนะนำให้ใช้ QR เมื่อไม่มีวิธียืนยัน และรหัส 22 แจ้งว่าบัญชีถูกปิดใช้งาน ไม่มีคำตอบเหล่านี้ถูกลองใหม่เองอัตโนมัติ

## การคงการเข้าสู่ระบบไว้

- **เปิดแอปตอนไม่มีเครือข่าย** `login()` จะคืน `LINE_RETRY` ก็ต่อเมื่อ `transient_failure()` บอกว่าความล้มเหลวอาจเกิดจากเครือข่าย ได้แก่ ไม่มีคำตอบ HTTP เลย HTTP 408, 429 หรือ 5xx หรือช่วงพักในเครื่อง UI จึงเก็บเซสชันไว้แล้วลองใหม่ (`retry_login()` ใน `ui.c`) หลัง 5, 10, 20… วินาที สูงสุดทุกห้านาที พร้อมแสดงว่า "Still signed in" ระหว่างช่วงพัก การลองใหม่เหล่านั้นจะล้มเหลวในเครื่องโดยไม่ส่งคำขอ
- **การปฏิเสธของ LINE เองหยุดการลองใหม่** TalkException ใด ๆ หรือ HTTP 4xx เช่น 401 หรือ 403 จะจบความพยายามด้วย "LINE refused this desktop session" เซสชันยังบันทึกอยู่ แต่จะไม่มีอะไรลองใหม่จนกว่าผู้ใช้จะเลือกลงชื่อเข้าใช้ 401 หรือ 403 จะได้การต่ออายุโทเค็นหนึ่งครั้งและ `getProfile` อีกหนึ่งครั้งก่อน (`checked_profile()`)
- **การถูกปฏิเสธ** `session_rejected()` ใน `main.c` ถือว่าตัวล็อก (`s->denied`), `LINE_SESSION_EXPIRED` และ TalkException รหัส 1, 7, 8, 14 และ 17 หมายถึง "LINE ยุติเซสชันนี้แล้ว" worker ลืมเซสชัน (`forget()`) และ UI กลับไปหน้าลงชื่อเข้าใช้พร้อมเหตุผล ดู [พื้นฐานโปรโตคอล](protocol-basics.md)
- **การต่ออายุ** อธิบายไว้ใน [พื้นฐานโปรโตคอล](protocol-basics.md)
- **เดสก์ท็อปอื่นลงชื่อเข้าใช้** อาจทำให้ LINE ยุติเซสชันนี้ ซึ่งจะรู้ได้จากการถูกปฏิเสธในคำขอหรือการตรวจ revision ครั้งถัดไป

## การออกจากระบบ

**Sign out** ส่ง `logout` worker เรียก `logoutV2` บน `/AS4` (ไม่มีอาร์กิวเมนต์) เพื่อยุติเซสชันของอุปกรณ์ที่เชื่อมที่ฝั่ง LINE แล้วลบเซสชันในเครื่องด้วย `line_store_forget()` ทุกครั้ง การออกจากระบบบนคอมพิวเตอร์นี้ไม่ขึ้นกับคำตอบของ LINE คำตอบจะเป็น `{"confirmed": true}` เมื่อ LINE ยุติเซสชันแล้ว หรือเซสชันตายไปแล้ว (ถูกปฏิเสธ หรือ `s->denied`) และเป็น `false` เมื่อคำขอล้มเหลว เช่น ไม่มีเครือข่าย ระหว่างช่วงพักจาก `Retry-After` หรือสัญญาณว่าเซิร์ฟเวอร์ไม่ว่าง worker จะข้าม `logoutV2` และคำตอบก็เป็น `false` เช่นกัน เมื่อเป็น `false` หน้าต่างจะแจ้งว่าออกจากระบบบนคอมพิวเตอร์นี้แล้ว และขอให้ผู้ใช้ตรวจสอบอุปกรณ์ที่เชื่อมต่อในโทรศัพท์ มีเพียงกรณีลบไฟล์เซสชันไม่สำเร็จเท่านั้นที่ผู้ใช้จะยังอยู่ในระบบ UI ปิดโปรแกรมเบราว์เซอร์และรีเซ็ตทุกโมดูล

การออกจากระบบไม่ต้องมีเซสชันที่ทำงานอยู่ เมื่อมีเซสชันบันทึกไว้แต่ยังไม่ได้เข้าสู่ระบบ (ติดต่อ LINE ไม่ได้ หรือ LINE ปฏิเสธด้วยรหัสที่ไม่ได้ยุติเซสชัน) ปุ่มหลักของหน้าลงชื่อเข้าใช้จะเป็น **Sign in** ซึ่งกลับเข้าเซสชันที่บันทึกไว้ และปุ่มที่สองจะเป็น **Sign out of the saved session** แทนปุ่มสลับ QR/อีเมล ปุ่มนี้เริ่ม worker ถ้ายังไม่มี แล้วส่ง `logout` worker จัดการ `logout` ก่อนตรวจว่าเซสชันพร้อม โดยเปิดที่เก็บเอง ถ้าเวอร์ชันนี้อ่านไฟล์เซสชันไม่ได้ จะลบไฟล์โดยไม่อ่านด้วย `line_store_discard()` และตอบ `{"confirmed": false}` เพราะไม่มีโทเค็นให้เพิกถอน เมื่อเซสชันที่บันทึกไว้หายไปแล้ว หน้าจอจะกลับมาให้ลงชื่อเข้าใช้ด้วย QR หรืออีเมลอีกครั้ง

## ไฟล์เซสชัน

[`state.c`](../../src/state.c) เก็บอ็อบเจกต์ JSON หนึ่งตัวใน `$XDG_STATE_HOME/avernella/session.json`

```json
{
  "access": "<access token>",
  "refresh": "<refresh token>",
  "mid": "u0123456789abcdef0123456789abcdef",
  "refreshAt": 1766000000,
  "keys": {
    "active": 7,
    "own":    {"6": "<กุญแจส่วนตัวแบบ base64>", "7": "<กุญแจส่วนตัวแบบ base64>"},
    "peers":  {"u…/12": "<กุญแจสาธารณะแบบ base64>"},
    "groups": {"c…/3": "<กุญแจส่วนตัวของกลุ่มแบบ base64>"}
  },
  "seq": 1234
}
```

| คีย์ | ความหมาย |
| ---- | -------- |
| `access`, `refresh` | โทเค็น เป็น ASCII ที่พิมพ์ได้ ยาวไม่เกิน 16 KiB ต่อตัว |
| `mid` | MID ของคุณ ไม่มีในเซสชันที่บันทึกก่อน `getProfile` ครั้งแรก |
| `refreshAt` | เวลา Unix ที่ LINE ต้องการให้ต่ออายุโทเค็น ถ้าเป็น 0 หรือไม่มีแปลว่า "ต่ออายุเลย" |
| `keys.active` | key ID ของรุ่นกุญแจ Letter Sealing ปัจจุบันของคุณ |
| `keys.own` | กุญแจส่วนตัวทุกรุ่นที่โทรศัพท์แชร์มา ใช้ key ID เป็นคีย์ |
| `keys.peers` | แคชกุญแจสาธารณะของผู้ใช้อื่น คีย์คือ `<mid>/<key id>` |
| `keys.groups` | แคชกุญแจกลุ่มที่แกะแล้ว คีย์คือ `<chat>/<key id>` |
| `seq` | หมายเลขลำดับคำขอสูงสุดที่อาจถูกใช้ไปแล้ว |

`load()` ปฏิเสธไฟล์ เว้นแต่จะเป็นไฟล์ปกติที่คุณเป็นเจ้าของ กลุ่มและคนอื่นอ่านไม่ได้ ขนาดระหว่าง 1 ไบต์ถึง 8 MiB เป็น JSON ที่ถูกต้อง มี `access` ที่ไม่ว่าง มี `keys` เป็นอ็อบเจกต์ และ `seq` เป็นจำนวนเต็มตั้งแต่ 0 ถึง 2³¹−1 บัฟเฟอร์ที่ถือข้อมูลไฟล์และสตริงโทเค็นที่แยกวิเคราะห์ได้ถูกล้างหลังแยกวิเคราะห์

เมื่อการบันทึกขาดตอน worker ตัวถัดไปที่ได้สิทธิ์ล็อกเซสชันจะลบไฟล์ `session.new` ที่ค้างอยู่ก่อนกู้คืนเซสชัน หากบันทึกไม่สำเร็จ แอปจะพยายามลบไฟล์ชั่วคราวนั้นทันที

`line_store_save()` เขียน `session.new` ด้วย `O_EXCL | O_NOFOLLOW` และโหมด 0600 `fdatasync` แล้ว rename ทับ `session.json` และ `fsync` ไดเรกทอรี ถ้า JSON จะใหญ่เกิน 8 MiB จะทิ้งแคช `peers` และ `groups` ก่อน เพราะดึงใหม่ได้ แต่เก็บกุญแจของคุณเองและโทเค็นไว้ เพราะสร้างใหม่ไม่ได้ ข้อความ JSON ที่เขียนและสตริงโทเค็นในนั้นถูกล้างหลังเขียนเสร็จ

worker บันทึกเซสชันใหม่ทุกครั้งที่ `s->token_changed` ถูกตั้ง: หลังการจับคู่ การต่ออายุ โทเค็นที่ถูกหมุนเวียน หรือกำหนดการต่ออายุใหม่

### ลำดับคำขอ

RPC ทุกตัวที่เปลี่ยนสถานะต้องแนบหมายเลขลำดับคำขอ (`reqSeq`) และ LINE คาดว่ามันจะไม่ซ้ำกันเลยสำหรับอุปกรณ์หนึ่ง `line_store_sequence()` แจกหมายเลขจากช่วงที่จองไว้

- `s->seq` คือหมายเลขล่าสุดที่ใช้ `s->seq_reserved` คือปลายช่วงที่บันทึกลงดิสก์
- เมื่อช่วงหมด จะจองเพิ่มอีก 32 ตัว และ **บันทึกไฟล์ก่อนคืน** หมายเลขถัดไป
- ตอนเริ่มใหม่ `seq` ถูกโหลดเป็นค่าสูงสุดที่บันทึกไว้ ช่วงที่เคยจองไว้ทั้งหมดจึงนับว่าใช้ไปแล้ว

`dispatch()` ใน `main.c` เรียก `reserve_sequence()` ก่อนคำขอที่เปลี่ยนสถานะแต่ละครั้ง แล้วลด `s->seq` ลงหนึ่ง เพื่อให้ `++s->seq` ในฟังก์ชันส่งตกที่หมายเลขที่จองไว้ ฟังก์ชันที่รับ `reserved_seq` เป็นอาร์กิวเมนต์จะใช้ค่านั้นตรง ๆ

ทำไมต้องระวังขนาดนี้? คำขอที่หมดเวลาอาจไปถึง LINE แล้ว การใช้หมายเลขซ้ำอาจทำให้ LINE ถือว่าข้อความใหม่เป็นข้อความซ้ำ เมื่อลำดับถึง 2³¹−1 ผู้ใช้ต้องจับคู่ใหม่

### ความปลอดภัย

ไฟล์เซสชันเก็บโทเค็นและกุญแจส่วนตัว Letter Sealing **เป็นข้อความธรรมดา** ป้องกันด้วยสิทธิ์ของไฟล์และไดเรกทอรีโหมด 0700 เท่านั้น ใครที่อ่านไฟล์นี้ได้ก็สวมรอยเป็นอุปกรณ์ที่เชื่อมนี้และอ่านข้อความที่เข้ารหัสได้ worker ถือ `flock` แบบ exclusive บนไดเรกทอรีตลอดที่รัน Avernella สองตัวจึงใช้เซสชันเดียวกันไม่ได้
