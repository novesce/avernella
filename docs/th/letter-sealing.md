# Letter Sealing (การเข้ารหัสต้นทางถึงปลายทาง)

[สารบัญ](README.md) · ก่อนหน้า: [ข้อความ](messaging.md) · ถัดไป: [มีเดีย](media.md)

Letter Sealing คือการเข้ารหัสข้อความแบบต้นทางถึงปลายทางของ LINE เซิร์ฟเวอร์ของ LINE ส่งต่อและเก็บข้อความที่ปิดผนึกไว้ได้ แต่อ่านไม่ได้ ทุกอย่างในหน้านี้อยู่ใน [`sealing.c`](../../src/sealing.c) การออกแบบที่เปิดเผยอยู่ใน [เอกสารการเข้ารหัสของ LINE](https://www.lycorp.co.jp/en/privacy-security/line-encryption-whitepaper-ver2.2.pdf) และรูปแบบไบต์ที่แน่นอนตรวจทานกับโค้ดของ LINEJS ซึ่งเป็นโปรเจกต์ที่ทำงานร่วมกับ LINE ได้ (อ้างถึงใน [analysis/portability.md](../../analysis/portability.md))

## หลักการแบบเข้าใจง่าย

- ทุกบัญชีมี **คู่กุญแจ X25519** แต่ละคู่คือ **รุ่นของกุญแจ** ที่มีหมายเลข เรียกว่า **key ID** เมื่อบัญชีสร้างคู่ใหม่ (เช่น หลังติดตั้ง LINE บนโทรศัพท์ใหม่) รุ่นเก่ายังอยู่ ข้อความเก่าจึงยังเปิดได้
- ทุกอุปกรณ์ของบัญชีต้องมีกุญแจ **ส่วนตัว** เดสก์ท็อปเครื่องใหม่ได้กุญแจเหล่านี้จากโทรศัพท์ตอนลงชื่อเข้าใช้ ในรูป **key chain** ที่เข้ารหัสไว้
- เมื่อส่งถึงใครสักคน คุณรวมกุญแจส่วนตัวของ *คุณ* เข้ากับกุญแจสาธารณะของ *เขา* (X25519 Diffie–Hellman) ทั้งสองฝ่ายได้ **ความลับร่วม** ตัวเดียวกันโดยไม่ต้องส่งมันไปไหน แล้วสร้างกุญแจสำหรับข้อความแต่ละข้อความจากความลับร่วมนั้น
- กลุ่มมีคู่กุญแจของตัวเอง เรียกว่า **กุญแจกลุ่ม** กุญแจส่วนตัวของกลุ่มถูกเข้ารหัสแยกให้สมาชิกแต่ละคนด้วยกุญแจสาธารณะของเขา สมาชิกแต่ละคนจึงแกะออกมาได้
- ข้อความแต่ละข้อความบอก key ID ที่ใช้ ผู้รับจึงรู้ว่าต้องเลือกรุ่นไหน

## การได้มาซึ่ง key chain

ตอนลงชื่อเข้าใช้ (ด้วย QR หรืออีเมล ดู [การลงชื่อเข้าใช้](sign-in.md)) เดสก์ท็อปสร้างคู่กุญแจ X25519 ใหม่และให้กุญแจสาธารณะแก่โทรศัพท์ โทรศัพท์ตอบกลับด้วย

| ฟิลด์ | ความหมาย |
| ----- | -------- |
| `publicKey` | กุญแจสาธารณะ X25519 ของโทรศัพท์สำหรับการแลกเปลี่ยนนี้ (base64, 32 ไบต์) |
| `encryptedKeyChain` | key chain ที่เข้ารหัสด้วย AES-256-CBC (base64) |
| `hashKeyChain` | MAC ขนาด 16 ไบต์ของ chain ที่เข้ารหัส (base64, อาจไม่มี) |
| `keyId` | ID ของรุ่นที่บัญชีใช้งานอยู่ |

`line_import_login_keys()` ทำดังนี้

1. `shared = X25519(กุญแจส่วนตัวของเดสก์ท็อป, กุญแจสาธารณะของโทรศัพท์)`
2. `key = SHA-256(shared ‖ "Key")` และ `iv = fold(SHA-256(shared ‖ "IV"))` **fold** คือการ XOR 16 ไบต์หลังของแฮช 32 ไบต์เข้ากับ 16 ไบต์แรก (`fold_digest()`)
3. ถ้ามี MAC (มีเสมอเมื่อลงชื่อด้วยอีเมล) ให้ตรวจ: `MAC = AES-256-ECB(key, fold(SHA-256(encryptedKeyChain)))` (`chain_proof()`) เทียบแบบเวลาคงที่
4. ถอดรหัส chain ด้วย AES-256-CBC โดยใช้ `key` และ `iv`
5. plaintext คือ **struct ของ Thrift แบบ Compact** ฟิลด์ 1 เป็นรายการ แต่ละรายการมีฟิลด์ 2 คือ key ID ฟิลด์ 4 คือกุญแจสาธารณะ 32 ไบต์ และฟิลด์ 5 คือกุญแจส่วนตัว 32 ไบต์
6. สำหรับทุกรายการ คำนวณกุญแจสาธารณะใหม่จากกุญแจส่วนตัวแล้วต้องตรงกัน ปฏิเสธรายการซ้ำ และต้องมี ID ที่ใช้งานอยู่ (`key_generations()`)
7. เมื่อทุกอย่างถูกต้องแล้วเท่านั้น จึงแทนที่ `s->keys` ด้วย

   ```json
   {"active": 7, "own": {"6": "<กุญแจส่วนตัว b64>", "7": "<กุญแจส่วนตัว b64>"}, "peers": {}}
   ```

สำหรับการลงชื่อด้วยอีเมล MAC ยังถูกคืนเป็น **proof** 16 ไบต์ที่ส่งไปกับ `confirmE2EELogin` ความลับระหว่างทางทั้งหมดถูกล้างด้วย `OPENSSL_cleanse`

## การได้กุญแจสาธารณะของคนอื่น

`peer_key()` ดึงกุญแจสาธารณะของผู้ติดต่อ มีสองกรณี

**ตอนส่ง** (ต่อรองกุญแจปัจจุบัน): `negotiateE2EEPublicKey` บน `/S4` ด้วย `{2: MID ของอีกฝ่าย}` คำตอบ

| ฟิลด์ | ความหมาย |
| ----- | -------- |
| 1 | ชนิดเนื้อหาที่อนุญาต (รายการ i32) |
| 2 | กุญแจสาธารณะ: ฟิลด์ 2 คือ key ID ฟิลด์ 4 คือกุญแจ 32 ไบต์ |
| 3 | เวอร์ชันของข้อกำหนด ต้องเป็น 2 |

ถ้าเวอร์ชันไม่ใช่ 2 หรือชนิดเนื้อหาไม่ได้รับอนุญาต การส่งจะล้มเหลวด้วย "This contact does not accept Letter Sealing v2 for this message type" การตรวจชนิดที่อนุญาตใช้กับเนื้อหาในตัวข้อความเท่านั้น (ข้อความ 0 และตำแหน่ง 15) ไฟล์แนบใช้เส้นทางมีเดียแยกต่างหาก

**ตอนอ่าน** (ต้องเป็นรุ่นที่ข้อความระบุ): ดูแคช `keys.peers["<mid>/<id>"]` ก่อน แล้วจึง `getE2EEPublicKey` ด้วย `{2: peer, 3: 1, 4: key ID}` ถ้าเส้นทางนี้ไม่มีเมธอดนั้น จะถอยไปใช้การต่อรอง แต่ยอมรับคำตอบก็ต่อเมื่อเป็นรุ่นที่ขอเท่านั้น

กุญแจถูกแคชไว้ใน `keys.peers` และบันทึกไปกับเซสชัน

## กุญแจกลุ่ม

`group_private_key()` ดึงกุญแจส่วนตัวของกลุ่ม

**ตอนส่ง** ใช้กุญแจกลุ่มล่าสุด: `getLastE2EEGroupSharedKey` ด้วย `{2: 1, 3: chat}` **ตอนอ่าน** ใช้รุ่นที่ข้อความระบุ: ดูแคช `keys.groups["<chat>/<id>"]` ก่อน แล้วจึง `getE2EEGroupSharedKey` ด้วย `{2: 1, 3: chat, 4: group key ID}`

คำตอบ

| ฟิลด์ | ความหมาย |
| ----- | -------- |
| 2 | group key ID |
| 3 | MID ของผู้สร้าง (ผู้ที่ห่อสำเนานี้) |
| 4 | key ID ของผู้สร้าง |
| 5 | MID ของผู้รับ (ต้องเป็นคุณ) |
| 6 | key ID ของผู้รับ (หนึ่งในรุ่นของคุณ) |
| 7 | กุญแจส่วนตัวของกลุ่มที่ห่อไว้ 48 ไบต์ |
| 8 | ชนิดเนื้อหาที่อนุญาต (เฉพาะกุญแจล่าสุด) |
| 9 | เวอร์ชันของข้อกำหนด ต้องเป็น 2 (เฉพาะกุญแจล่าสุด) |

การแกะ: `shared = X25519(กุญแจส่วนตัวของคุณ [key ID ของผู้รับ], กุญแจสาธารณะของผู้สร้าง [key ID ของผู้สร้าง])` แล้วสร้าง `key`/`iv` แบบเดียวกับ key chain แล้วถอดรหัส AES-256-CBC ผลลัพธ์ต้องยาว 32 ไบต์พอดี และถูกแคชใน `keys.groups`

## ข้อความใช้ความลับตัวไหน

`message_shared_secret()` เลือกข้อมูลตั้งต้น

| แชต | ตอนส่ง | ตอนอ่าน |
| --- | ------ | ------- |
| ตัวต่อตัว | `X25519(กุญแจส่วนตัวของคุณ [ID ที่ใช้งาน], กุญแจสาธารณะของอีกฝ่าย [ID ปัจจุบันของเขา])` | ข้อความของคุณเอง: `X25519(กุญแจส่วนตัวของคุณ [ID ผู้ส่ง], กุญแจสาธารณะของอีกฝ่าย [ID ผู้รับ])` ข้อความของเขา: `X25519(กุญแจส่วนตัวของคุณ [ID ผู้รับ], กุญแจสาธารณะของผู้ส่ง [ID ผู้ส่ง])` |
| กลุ่มหรือห้อง | `X25519(กุญแจส่วนตัวของกลุ่ม [group key ID ล่าสุด], กุญแจสาธารณะของคุณ [ID ที่ใช้งาน])` | `X25519(กุญแจส่วนตัวของกลุ่ม [group key ID ในข้อความ], กุญแจสาธารณะของผู้ส่ง [key ID ของผู้ส่ง])` |

ในกลุ่ม ช่อง "key ID ของผู้รับ" ในซองจดหมายบรรจุ **group key ID** `public_by_id()` คืนกุญแจสาธารณะของคุณเอง ซึ่งคำนวณจากกุญแจส่วนตัว เมื่อผู้ส่งคือคุณ

## ซองจดหมายของข้อความ

ข้อความที่ปิดผนึกมี `contentMetadata.e2eeVersion` เป็น `"1"` หรือ `"2"` (ถ้าไม่มีหมายถึง 2) และมี **chunk ห้าตัว** พอดีใน Message ฟิลด์ 20

### เวอร์ชัน 2 (ที่ไคลเอนต์ส่ง)

| Chunk | เนื้อหา |
| ----- | ------- |
| 0 | salt สุ่ม 16 ไบต์ |
| 1 | ciphertext ตามด้วยแท็ก GCM 16 ไบต์ |
| 2 | nonce สุ่ม 12 ไบต์ (ฝั่งอ่านรับได้ 1 ถึง 32) |
| 3 | key ID ของผู้ส่ง 4 ไบต์ big-endian |
| 4 | key ID ของผู้รับ (หรือ group key ID) 4 ไบต์ big-endian |

- `key = SHA-256(shared ‖ salt ‖ "Key")`
- การเข้ารหัส: **AES-256-GCM** ด้วยกุญแจและ nonce นั้น
- **ข้อมูลยืนยันเพิ่มเติม (AAD)** ขนาด 82 ไบต์ (`make_aad()`): MID `to` (33 ไบต์) ‖ MID `from` (33) ‖ key ID ผู้ส่ง (4, big-endian) ‖ key ID ผู้รับ (4) ‖ เวอร์ชัน `2` (4) ‖ ชนิดเนื้อหา (4) แท็กจึงปกป้องด้วยว่าข้อความมาจากใครถึงใคร ใช้กุญแจตัวไหน และเป็นเนื้อหาชนิดไหน เซิร์ฟเวอร์ที่สลับผู้รับหรือเปลี่ยนป้ายรูปให้เป็นข้อความจะทำให้แท็กไม่ผ่าน

### เวอร์ชัน 1 (อ่านอย่างเดียว)

| Chunk | เนื้อหา |
| ----- | ------- |
| 0 | salt 8 ไบต์ |
| 1 | ciphertext เป็นจำนวนเท่าของ 16 ไบต์ |
| 2 | MAC 16 ไบต์ |
| 3, 4 | key ID ของผู้ส่งและผู้รับ |

- `key = SHA-256(shared ‖ salt ‖ "Key")`, `iv = fold(SHA-256(shared ‖ salt ‖ "IV"))`
- ตรวจ MAC ก่อน: `AES-256-ECB(key, fold(SHA-256(ciphertext)))` ต้องเท่ากับ chunk 2
- แล้วจึงถอดรหัส **AES-256-CBC**

### plaintext

ไบต์ที่ถอดรหัสแล้วต้องเป็นอ็อบเจกต์ JSON แบบเคร่งครัดเพียงตัวเดียว เป็น UTF-8 ที่ถูกต้อง และไม่มีอะไรตามหลัง สำหรับข้อความคือ `{"text": "…"}` อาจมี `REPLACE` สำหรับอีโมจิ LINE สำหรับไฟล์แนบคือ `{"keyMaterial": "…", "fileName": "…"}` (ดู [มีเดีย](media.md)) ชนิดเนื้อหาที่ส่งให้ `line_seal_payload()` และ `line_open_payload()` ต้องตรงกับฟิลด์ 15 ของข้อความ เพราะเป็นส่วนหนึ่งของ AAD

## API

| ฟังก์ชัน | ทำอะไร |
| -------- | ------ |
| `line_import_keys(s, meta, secret, &error)` | นำเข้า key chain จากโทรศัพท์ (ลงชื่อด้วย QR) |
| `line_import_login_keys(s, meta, secret, proof, &error)` | เหมือนกัน และคืน proof ด้วย (ลงชื่อด้วยอีเมล) |
| `line_seal_payload(s, chat, content_type, payload, &error)` | เข้ารหัสอ็อบเจกต์ JSON สำหรับแชต คืน chunk ห้าตัว |
| `line_open_payload(s, message, content_type, &error)` | ถอดรหัส Message ดิบ คืนอ็อบเจกต์ JSON |
| `line_seal_text()`, `line_open_text()` | ทางลัดสำหรับ `{"text": …}` |

ข้อผิดพลาด

- `LINE_OWN_KEY_MISSING`: ข้อความใช้กุญแจรุ่นหนึ่งของ *คุณ* ที่อุปกรณ์นี้ไม่เคยได้รับ UI แสดงข้อความว่ากุญแจหายไปจากอุปกรณ์นี้ ไม่มีทางแก้นอกจากให้โทรศัพท์แชร์กุญแจรุ่นนั้นมา
- "Letter Sealing could not authenticate this message": แท็กหรือ MAC ไม่ตรง
- "…unsupported chat type or Letter Sealing version": เวอร์ชันที่ไม่รู้จัก ชนิดเนื้อหาผิด หรือข้อความตัวต่อตัวที่ไม่ได้มาจากหรือส่งถึงคุณ

## แคชความลับร่วม

การเปิดประวัติยาว ๆ จะต้องคำนวณ X25519 ซ้ำเดิมสำหรับทุกข้อความ `line_open_payload()` จึงแคชความลับร่วมไว้ใน `s->history_secrets` เป็นวงแหวน 32 ช่องที่ใช้ (to, from, key ID ผู้ส่ง, key ID ผู้รับ) เป็นคีย์ และเพิ่มเข้าแคช **หลัง** ข้อความผ่านการยืนยันแล้วเท่านั้น การนำเข้า key chain ใหม่หรือการออกจากระบบจะล้างทั้งอาร์เรย์ `tests/sealing.c` มีเคสวัดประสิทธิภาพ (`/sealing/authenticated-history-cache`) ที่วัดประโยชน์ของแคชนี้

## สิ่งที่ไม่ได้เข้ารหัส

- `contentMetadata`: ชนิดเนื้อหา การเมนชัน รหัสสติกเกอร์ รหัส object ของไฟล์แนบ ขนาดไฟล์ LINE ต้องใช้ข้อมูลเหล่านี้ในการส่งและการแจ้งเตือน
- ประกาศ (LINE เก็บเป็นข้อความธรรมดา)
- สติกเกอร์ (อ้างถึงภาพสาธารณะ)
- ข้อมูลโปรไฟล์ ชื่อกลุ่ม และรายชื่อสมาชิก

ข้อมูล `REPLACE` สำหรับอีโมจิ LINE ในข้อความ *อยู่* ใน payload ที่ปิดผนึก กุญแจของไฟล์แนบก็เช่นกัน
