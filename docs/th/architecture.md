# สถาปัตยกรรม

[สารบัญ](README.md) · ก่อนหน้า: [การ build](building.md) · ถัดไป: [ส่วนติดต่อผู้ใช้](ui.md)

หน้านี้อธิบายส่วนประกอบที่ทำงานอยู่: มีโปรเซสและเธรดอะไรบ้าง แต่ละตัวแตะอะไรได้ สื่อสารกันอย่างไร และเขียนอะไรลงดิสก์ อ่านหน้านี้ก่อนแก้อะไรก็ตามที่ข้ามเส้นแบ่งระหว่างโปรเซสหรือเธรด

## ภาพใหญ่

Avernella เป็นโปรแกรมไฟล์เดียวชื่อ `avernella` ที่ทำงานเป็น **สองโปรเซส** และมี **โปรแกรมเบราว์เซอร์** เสริมอีกตัวหนึ่ง

```
┌──────────────────────────── avernella (โปรเซส UI) ──────────────────────────────┐
│ หน้าต่าง SDL · วาดด้วย Cairo/Pango · โมดูล Vulkan · ถอดรหัสรูป · tray ·            │
│ การแจ้งเตือน · เสียง · portal (จับภาพหน้าจอ) · คลิปบอร์ด · ฉบับร่างในหน่วยความจำ    │
└───────┬───────────────────────────────┬──────────────────────────────┬──────────┘
        │ JSON ทีละบรรทัด                │ เฟรมวิดีโอคอล                 │ datagram คั่นด้วยแท็บ
        │ (socketpair SOCK_STREAM,      │ (SOCK_SEQPACKET, memfd ที่    │ (SOCK_SEQPACKET, fd 3)
        │  เป็น stdin/stdout ของ worker) │  ปิดผนึกแล้ว ส่งด้วย SCM_RIGHTS) │
┌───────┴───────────────────────────────┴────────┐          ┌──────────┴───────────┐
│ avernella --worker (โปรเซส worker)              │          │ avernella-liff       │
│ เซสชัน โทเค็น กุญแจ Letter Sealing · RPC ·       │          │ (WPE WebKit หรือ     │
│ อัปโหลด/ดาวน์โหลดมีเดีย · เธรด sync · เธรดรูป     │          │ avernella-liff-gtk)  │
│ · เธรดการโทร · การจับภาพหน้าจอ                   │          │ แอป LINE (LIFF)      │
└───────┬────────────────────────────────────────┘          └──────────┬───────────┘
        │ HTTPS (libcurl, HTTP/2)        UDP (การโทร)                   │ HTTPS
  legy.line-apps.com · obs.line-apps.com · CDN ของ LINE · relay การโทร   เว็บไซต์ของแอปนั้น
```

การแบ่งแบบนี้มีเป้าหมายเดียว: **โปรเซสที่วาดเนื้อหาซึ่งเชื่อถือไม่ได้จะไม่ถือข้อมูลยืนยันตัวตน LINE ของคุณ และโปรเซสที่ถือข้อมูลยืนยันตัวตนจะไม่วาดอะไรเลย** รูป การ์ด Flex และ rich message จากคนแปลกหน้าถูกถอดรหัสและวาดในโปรเซส UI ส่วนโทเค็นและกุญแจส่วนตัว Letter Sealing อยู่ภายใต้การดูแลของ worker และ Key Vault หน้าเว็บของแอป LINE รันในโปรเซสที่สามซึ่งมี sandbox ของตัวเอง

worker เปิดโปรเซสควบคุม Key Vault ก่อนอ่านข้อมูลยืนยันตัวตนและเปิด sandbox ทั้งสองโปรเซสสื่อสารผ่านคู่ซ็อกเก็ต Unix แบบไม่มีชื่อ เมื่อ Key Vault หลุด โปรเซสควบคุมจะเปิดตัวใหม่เพื่อโหลดกุญแจ Letter Sealing และขอบเขตลำดับคำขอที่บันทึกไว้ผ่านตัวระบุไดเรกทอรีที่ล็อกอยู่ การดำเนินการภายในเครื่องที่ทำซ้ำได้จะลองอีกครั้งหลังเชื่อมต่อ ส่วนคำขอที่ส่งไปยัง LINE แล้วใช้กฎการลองใหม่เดิม

worker จะเริ่มทำงานได้เมื่อปิดตัวระบุไฟล์ที่รับสืบทอดมานอกช่อง IPC แล้ว บนเคอร์เนลที่รองรับ Landlock นั้น Key Vault สามารถอ่าน สร้าง แทนที่ และลบไฟล์ปกติในไดเรกทอรีสถานะของ Avernella โดยเปิดเซสชันที่บันทึกไว้ผ่านตัวระบุไดเรกทอรีที่ worker ส่งมา

## โปรเซส UI

`main()` ใน [`main.c`](../../src/main.c) เรียก `line_ui()` ใน [`ui.c`](../../src/ui.c) เว้นแต่อาร์กิวเมนต์แรกเป็น `--worker` หรือ `--worker-password` โปรเซส UI รับผิดชอบ

- หน้าต่าง SDL อินพุต คลิปบอร์ด และการลากวางไฟล์
- การวาดด้วย Cairo และ Pango แล้วนำเสนอผ่านโมดูล Vulkan แบบเนทีฟ ตัววาด Vulkan ของ SDL หรือพื้นผิวหน้าต่างของ SDL
- การถอดรหัสรูป (JPEG, PNG, WebP, PNG เคลื่อนไหว) ในเธรดเบื้องหลัง
- รายการแชต ประวัติของแชตที่เปิดอยู่ และฉบับร่างทั้งหมด เก็บไว้ในหน่วยความจำ
- บริการของเดสก์ท็อปผ่าน D-Bus ได้แก่ tray การแจ้งเตือน และ portal จับภาพหน้าจอ
- การตั้งค่าแชต (โฟลเดอร์ หมุด การปิดเสียง ปุ่มลัด) ผ่าน [`chat_lists.c`](../../src/chat_lists.c)
- เสียง ผ่าน [`ui_sounds.c`](../../src/ui_sounds.c)
- การเริ่มและดูแล worker กับโปรแกรมเบราว์เซอร์

มันไม่เคยเปิดการเชื่อมต่อไปยังเซิร์ฟเวอร์ RPC ของ LINE เลย อะไรที่ต้องการจาก LINE จะขอผ่าน worker ทั้งหมด

## โปรเซส worker

worker ([`main.c`](../../src/main.c) เริ่มที่ `worker()`) เป็นโปรเซสเดียวที่ถือเซสชัน ได้แก่ access token และ refresh token, MID ของบัญชี, key chain ของ Letter Sealing และตัวนับลำดับคำขอ มันรัน RPC ทุกตัว เข้ารหัสและถอดรหัสข้อความ อัปโหลดและดาวน์โหลดมีเดีย และดูแลการโทร

### เริ่มต้นอย่างไร

UI เริ่ม worker ตอนพยายามลงชื่อเข้าใช้ครั้งแรก (หรือตอนเปิดแอปถ้ามีเซสชันบันทึกไว้) ใน `start_worker()` ของ `ui.c`

1. สร้าง socketpair แบบ `SOCK_STREAM` สำหรับ JSON และ socketpair แบบ `SOCK_SEQPACKET` สำหรับเฟรมวิดีโอคอล
2. รัน `posix_spawn("/proc/self/exe", ["avernella", "--worker"])` พร้อม file action ที่ทำให้ซ็อกเก็ต JSON เป็น **stdin และ stdout** ของ worker และให้ซ็อกเก็ตเฟรมเป็น **fd 3** บน glibc 2.34 ขึ้นไป `posix_spawn_file_actions_addclosefrom_np` จะปิด descriptor อื่นที่สืบทอดมาทั้งหมด
3. สำหรับการลงชื่อด้วยอีเมล จะรัน `--worker-password` แทน ตอนนั้น fd 3 เป็นไปป์ที่บรรจุ `struct line_credentials` หนึ่งชุด (อีเมลและรหัสผ่าน ช่องละ 256 ไบต์) และซ็อกเก็ตเฟรมย้ายไปเป็น fd 4 worker อ่านไปป์ครั้งเดียว ปิด แล้วล้างบัฟเฟอร์ด้วย `explicit_bzero` UI ก็ล้างสำเนาของตัวเองด้วย รหัสผ่านจึงไม่เคยปรากฏในอาร์กิวเมนต์ ตัวแปรสภาพแวดล้อม หรือช่อง JSON

สิ่งแรกที่ worker ทำคือ `prctl(PR_SET_PDEATHSIG, SIGTERM)` เพื่อให้จบตามหน้าต่าง แล้วตรวจว่าโปรเซสแม่ยังไม่จบไปก่อน ซึ่งปิดช่องโหว่ของจังหวะเวลา

UI เริ่ม worker ด้วย `SDL_NO_SIGNAL_HANDLERS=1` เพื่อให้สัญญาณเมื่อโปรเซสแม่สิ้นสุดยังทำงานได้แม้เปิดเสียงโทรอยู่ เมื่อบังคับให้ worker ที่ขาดการเชื่อมต่อหยุดทำงานแล้ว หากยังต้องรอ `waitpid` จะให้เธรดแยกรอ หน้าต่างจึงยังรับอินพุตได้ขณะที่ไดรเวอร์เสียงหรือกราฟิกกำลังคืนทรัพยากรของโปรเซสลูก

### ลูปหลักของ worker

`worker()` รอใน `poll()` บน descriptor สี่ตัว และจัดการตัวที่พร้อม

| Descriptor | พร้อมเมื่อ | ตัวจัดการ |
| ---------- | ---------- | --------- |
| stdin | UI ส่งคำขอมาหนึ่งบรรทัด | `handle()` → `dispatch()` |
| `image_wake` (eventfd) | เธรดรูปดาวน์โหลดเสร็จ | `finish_images()` |
| eventfd ของ live-sync | เธรด long poll มี operation หรือโทเค็นที่ถูกหมุนเวียน | `live_operations()` |
| `timer` (timerfd แบบครั้งเดียว) | ถึงเวลางานบำรุงรักษา | `sync_revision()`: ต่ออายุโทเค็น หมดอายุคำเชิญโทร และตรวจ revision สำรองเมื่อ long poll มีปัญหา |

คำขอถูกประมวลผลทีละตัวตามลำดับ RPC ที่ช้าจึงทำให้คำขอถัดไปรอ ตั้งใจทำแบบนี้เพื่อให้สถานะเซสชันอยู่ในเธรดเดียว ส่วน long poll และการดาวน์โหลดแบบไม่ระบุตัวตนรันในเธรดของตัวเอง จึงไม่ต้องรอหลังการส่งข้อความ

## UI กับ worker คุยกันอย่างไร

### ช่อง JSON

แต่ละข้อความคืออ็อบเจกต์ JSON หนึ่งตัวในหนึ่งบรรทัด ปิดท้ายด้วย `\n` มีสามแบบ

**คำขอ (request)** ส่งจาก UI ไป worker และมี `id` เป็นตัวเลข

```json
{"id": 12, "method": "send", "params": {"chat": "u0123…", "text": "hi", "replyTo": "5123…"}}
```

**คำตอบ (reply)** ส่งกลับพร้อม `id` เดิม และมี `result` หรือ `error`

```json
{"id": 12, "result": {"id": "5124…", "sentAt": 1764000000000}}
{"id": 12, "error": "LINE declined sendMessage (service code 10)."}
```

ถ้า `login` ล้มเหลวเพราะเชื่อมต่อเครือข่ายไม่ได้ คำตอบจะมี `"retry": true` ด้วย UI จึงเก็บเซสชันไว้แล้วลองใหม่แบบเว้นระยะ แทนที่จะกลับไปหน้าลงชื่อเข้าใช้

**อีเวนต์ (event)** ส่งจาก worker ไป UI ไม่มี `id` แต่มีชื่อใน `event`

```json
{"event": "chat_message", "chat": "c0123…", "id": "5125…", "time": 1764000000000, "mine": false}
```

ฝั่ง worker ใช้ `line_emit()` เขียนอ็อบเจกต์ JSON ตามด้วยขึ้นบรรทัดใหม่ลง stdout ด้วย `writev` ภายใต้ mutex เพราะเธรดการโทรก็ส่งอีเวนต์ด้วย `line_event(name, key, value)` เป็นทางลัดสำหรับอีเวนต์ที่มีฟิลด์เดียว

ฝั่ง UI ใช้ `submit()` ใน `ui.c` กำหนด `id` ถัดไป เก็บ `struct ui_request` ที่บอกว่าจะทำอะไรกับคำตอบ เข้ารหัสบรรทัด แล้วปลุกเธรด `line-ipc` ผ่าน eventfd เมื่อคำตอบมาถึง `handle_packet()` จะหาคำขอจาก `id` แล้วเรียก `handle_reply()` คำตอบของคำขอหลัก (login, chats, history, send, หน้าเก่า, การแจ้งอ่าน, logout) จัดการใน `ui.c` ที่เหลือเป็นคำขอแบบ `MEDIA`: `handle_reply()` ยื่นคำตอบให้ `ui_liff_reply()`, `ui_profile_reply()`, `ui_find_reply()`, `ui_groups_reply()`, `ui_friends_reply()` และสุดท้าย `ui_media_reply()` โมดูลแรกที่รู้จักชื่อเมธอดจะเป็นผู้จัดการ โมดูลส่งคำขอแบบนี้ด้วย `ui_rpc(method, params, tag)` โดย `tag` คือหมายเลขของโมดูลเองไว้จับคู่กับคำตอบ

ตัวเลข **generation** ป้องกันคำตอบที่ค้างมาจากรอบเก่า: `stop_worker()` เพิ่ม `wire.generation` และแพ็กเก็ตที่ส่งมาจากเธรด `line-ipc` รุ่นเก่าจะถูกทิ้ง

### เมธอดของ worker

### ข้อมูลขนาดใหญ่: media lease

รูป ไฟล์ และภาพตัวอย่างวิดีโอใหญ่เกินกว่าจะใส่ในบรรทัด JSON worker จึงเขียนลง **memfd ที่ปิดผนึก** แทน (`line_media_lease()` ใน [`media_io.c`](../../src/media_io.c)): สร้างไฟล์ด้วย `memfd_create` (บน Linux 6.3 ขึ้นไปจะสร้างเป็นแบบรันโค้ดไม่ได้ด้วย `MFD_NOEXEC_SEAL`) เขียนข้อมูล เพิ่ม seal `F_SEAL_GROW | F_SEAL_SHRINK | F_SEAL_WRITE | F_SEAL_SEAL` แล้วตอบกลับว่า

```json
{"lease": "4b1c…-uuid"}
```

descriptor เดินทางไปพร้อมบรรทัดตอบกลับนั้น `emit_reply()` ใน `main.c` เปิด memfd ใหม่แบบอ่านอย่างเดียวผ่าน `/proc/self/fd` ของ worker เอง แล้วส่งไปกับไบต์แรกของบรรทัดเป็น `SCM_RIGHTS` (`line_wire_send()`) บน Unix stream socket เคอร์เนลจะจบการอ่านแต่ละครั้งทันทีหลังช่วงข้อมูลที่พา descriptor มา ดังนั้น `line_wire_read()` ในเธรด `line-ipc` ของ UI จึงมอบ descriptor ให้บรรทัดสุดท้ายที่เริ่มในการอ่านครั้งนั้น จากนั้น UI ใส่ descriptor ลงในผลลัพธ์ของคำตอบเป็น `"fd"` โดยลบ `"fd"` ที่ worker เขียนมาเองทิ้งก่อน `lease_fd()` ใน `ui_media.c` รับไปใช้ ตรวจว่าเป็นไฟล์ปกติที่มีขนาดตามคาด แล้วแมปหรืออ่าน UI ส่ง `releaseMedia` พร้อม lease เพื่อให้ worker ปิดสำเนาของตน และปิด descriptor ที่ไม่มีตัวจัดการคำตอบตัวไหนรับไป เนื่องจากไฟล์ถูกปิดผนึก UI จึงแมปได้โดยไม่ต้องกลัวว่าข้อมูลจะเปลี่ยนระหว่างใช้ เปิด lease ค้างไว้ได้พร้อมกันไม่เกินสี่ตัว

รุ่นก่อนหน้าส่งพาธ `/proc/<pid ของ worker>/fd/<n>` แทน ตอนนี้ worker ตั้งตัวเองเป็น non-dumpable (ดู [แซนด์บ็อกซ์ของ worker](#แซนด์บ็อกซ์ของ-worker)) เคอร์เนลจึงไม่ยอมให้โปรเซสอื่นใดเปิดพาธนั้น รวมทั้ง UI ด้วย

### เฟรมวิดีโอคอล

วิดีโอคอลเป็นสตรีมเดียวที่ไม่ผ่าน JSON เธรดการโทรเขียนเฟรมที่ถอดรหัสแล้ว (ระนาบ I420) ลง memfd ที่ปิดผนึกตัวใหม่ด้วย `pwritev` แล้วส่ง descriptor ผ่านซ็อกเก็ตเฟรม `SOCK_SEQPACKET` ด้วย `SCM_RIGHTS` พร้อมหัวข้อมูลเล็ก ๆ `struct line_preview_frame` (ขนาด การหมุน แหล่ง แชต เวลาที่ถอดรหัส) มีสามช่องสำหรับวิดีโอของอีกฝ่าย กล้องของคุณ และ presentation แบบแยก ในการโทรกลุ่ม ภาพหน้าจอที่ส่งผ่านกล้องจะใช้ช่องวิดีโอของผู้เข้าร่วมพร้อมธงระบุภาพหน้าจอ ส่วน presentation แบบเนทีฟใช้ช่องแยก จึงเปิดดูพร้อมกับกล้องของคนที่เลือกได้ เมื่อใช้ `callFrame` ผ่าน JSON แอปจะส่งเวลาที่ถอดรหัสไปด้วย เพื่อให้ UI ทิ้งเฟรมเก่าที่มาถึงหลังจากหยุดแชร์

เธรด `line-ipc` ของ UI รับ descriptor ใน `pump_preview()` และเก็บ **เฉพาะเฟรมล่าสุดของแต่ละแหล่ง** ถ้ามีเฟรมรออยู่แล้ว descriptor ตัวเก่าจะถูกปิดทิ้ง จากนั้นเธรดหลักอัปโหลดเฟรมเป็น texture บัฟเฟอร์ส่งของซ็อกเก็ตถูกตั้งให้เล็ก (4 KiB) โดยตั้งใจ หน้าต่างที่ยุ่งจึงไม่สะสมเฟรมเก่าค้าง การซ่อนหน้าต่างหรือหน้าจอการโทรจะหยุดส่งภาพตัวอย่าง ขณะที่การโทรยังดำเนินต่อ (`callPreview`)

### ช่องสื่อสารกับโปรแกรมเบราว์เซอร์

UI กับ `avernella-liff` ใช้ socketpair แบบ `SOCK_SEQPACKET` ที่ fd 3 ของเบราว์เซอร์ แต่ละ datagram คือข้อความหนึ่งข้อความที่คั่นฟิลด์ด้วยแท็บ (ดู [`liff_url.h`](../../src/liff_url.h)) รายละเอียดอยู่ในหน้า [LIFF](liff.md)

## ไฟล์บนดิสก์

Avernella เก็บข้อมูลน้อยมาก ข้อความ ประวัติ รายการแชต และฉบับร่าง **ไม่เคย** ถูกเขียนลงดิสก์

| พาธ | เขียนโดย | เนื้อหา |
| --- | -------- | ------- |
| `$XDG_STATE_HOME/avernella/session.json` (ค่าเริ่มต้น `~/.local/state/avernella/`) | worker, [`state.c`](../../src/state.c) | เซสชัน ดู [การลงชื่อเข้าใช้](sign-in.md) |
| `$XDG_STATE_HOME/avernella/session.new` | worker | ไฟล์ชั่วคราวระหว่างการบันทึกแบบ atomic |
| `$XDG_STATE_HOME/avernella/lists-<sha256(MID)>.json` | UI, [`chat_lists.c`](../../src/chat_lists.c) | การตั้งค่าแชตของแต่ละบัญชี: `folders`, `view` (โฟลเดอร์ที่เลือก), `pins`, `muted`, `bindings` (ปุ่มลัดที่เปลี่ยน), `notify`, `sounds`, `motion` |
| `$XDG_CONFIG_HOME/avernella/layout` (ค่าเริ่มต้น `~/.config/avernella/`) | UI, [`ui_theme.c`](../../src/ui_theme.c) | `avernella\n` หมายถึงเลือกธีม Avernella ค่าอื่นหรือไม่มีไฟล์หมายถึงธีม LINE ซึ่งเป็นค่าเริ่มต้น |
| `$XDG_CONFIG_HOME/avernella/` | UI, [`ui_lang.c`](../../src/ui_lang.c) | ภาษาของส่วนติดต่อที่เลือก |
| `$XDG_RUNTIME_DIR/avernella/` | UI, [`clipboard_paste.c`](../../src/clipboard_paste.c) | รูปที่วางเพื่อเตรียมส่ง ลบทิ้งหลังส่งหรือเมื่อปิดหน้าตัวอย่าง |
| `~/.cache/avernella/liff`, `~/.local/share/avernella/liff` | โปรแกรมเบราว์เซอร์ | แคช HTTP และคุกกี้ของ WebKit สำหรับแอป LINE |

กฎที่ผู้เขียนไฟล์ทุกตัวทำตาม

- **สิทธิ์แบบส่วนตัว** ไดเรกทอรีสร้างด้วยโหมด `0700` และไฟล์ `0600` (umask ของโปรเซสคือ `0077`) ฝั่งอ่านจะปฏิเสธไฟล์หรือไดเรกทอรีที่ผู้ใช้อื่นเป็นเจ้าของ หรือที่กลุ่มหรือคนอื่นอ่านได้
- **แทนที่แบบ atomic** เวอร์ชันใหม่เขียนลงไฟล์ชั่วคราวในไดเรกทอรีเดียวกัน `fdatasync` แล้ว rename ทับไฟล์เดิม และ `fsync` ไดเรกทอรี ถ้าเครื่องดับกลางทาง จะเหลือไฟล์เก่าหรือไฟล์ใหม่อย่างใดอย่างหนึ่ง
- **จำกัดขนาด** ไฟล์เซสชันใหญ่ได้ไม่เกิน 8 MiB และไฟล์การตั้งค่าแชต 2 MiB ไฟล์ที่ใหญ่กว่าจะถูกปฏิเสธโดยไม่อ่าน
- **เจ้าของคนเดียว** worker ถือ `flock` แบบ exclusive บนไดเรกทอรีเซสชันตลอดเวลาที่รัน

### การย้ายจากชื่อเก่า

Avernella เคยชื่อ *kitatide* และเริ่มต้นมาจาก *line-linux* ไฟล์ของทั้งสองมีรูปแบบเดียวกัน ข้อมูลจึงย้ายมาได้ แต่จะย้ายก็ต่อเมื่อ Avernella ยังไม่มีข้อมูลของตัวเองเท่านั้น

- **เซสชันและการตั้งค่าแชต** เมื่อยังไม่มี `$XDG_STATE_HOME/avernella` `migrate_store()` ใน `state.c` จะเลือกไดเรกทอรีรุ่นก่อนที่ใหม่ที่สุด คือ `kitatide` แล้วจึง `line-linux` และเปลี่ยนชื่อเป็น `avernella` ทั้งก้อนด้วย `renameat2(RENAME_NOREPLACE)` ภายใต้ล็อกของมัน ไดเรกทอรีที่มี `session.json` ซึ่งเวอร์ชันนี้อ่านไม่ได้จะถูกข้ามและปล่อยไว้ที่เดิม ถ้ามีไดเรกทอรี `avernella` อยู่แล้ว แม้จะออกจากระบบไปแล้ว ก็จะไม่ย้ายอะไรเลย
- **ข้อมูลเบราว์เซอร์ของแอป LINE** `line_liff_storage_dir()` ใน `liff_url.c` ทำแบบเดียวกันกับ `liff/` ใต้ไดเรกทอรีแคชและไดเรกทอรีข้อมูล ตอนที่เบราว์เซอร์เริ่มทำงานครั้งแรก

## เส้นทางของข้อความหนึ่งข้อความ ตั้งแต่ต้นจนจบ

**การส่ง** คุณพิมพ์ "hi" แล้วกด Enter

1. `send_message()` ใน `ui.c` เรียก `request(SEND, chat, text)` `ui_emoji_export()` แปลงอีโมจิ LINE ในฉบับร่างเป็นข้อความธรรมดาพร้อมช่วง `emojis` และ `mention_ranges()` เพิ่ม `mentions` ในแชตกลุ่ม ข้อความจะแสดงเป็นสถานะกำลังส่ง
2. `dispatch()` ของ worker ตรวจข้อความ (UTF-8 ยาวไม่เกิน 20,000 ไบต์) แล้วเรียก `reserve_sequence()` ซึ่งจองหมายเลขลำดับคำขอ และเมื่อชุดที่จองไว้ 32 ตัวหมด จะบันทึกค่าสูงสุดใหม่ลงดิสก์ **ก่อน** ส่งคำขอ เพราะการหมดเวลาอาจหมายความว่า LINE รับข้อความไปแล้ว หมายเลขจึงไม่ถูกใช้ซ้ำเด็ดขาด
3. `line_send_decorated()` ใน `messaging.c` สร้าง payload แล้ว `line_seal_payload()` ใน `sealing.c` เข้ารหัสด้วย Letter Sealing v2
4. `line_send_sealed()` เรียก `sendMessage` บน `/S4`
5. คำตอบมีรหัสข้อความใหม่ `show_sent()` ใน `ui.c` แทนแถวที่กำลังส่ง และล้างฉบับร่างถ้ายังไม่ถูกแก้หลังจากกดส่ง

**การรับ** อีกฝ่ายส่ง "hello" มา

1. LINE ตอบ long poll `sync` ที่ค้างอยู่บน `/SYNC4` ด้วย operation `RECEIVE_MESSAGE` (ชนิด 26)
2. เธรด `line-sync` เข้าคิวไว้แล้วส่งสัญญาณผ่าน eventfd
3. `live_operations()` ของ worker เรียก `message_operation()` ซึ่งส่งอีเวนต์ `chat_message` และทำเครื่องหมายว่าประวัติที่แคชไว้ของแชตนั้นล้าสมัย ถ้าแชตนั้นเปิดอยู่ `revalidate_history()` จะดึงหน้าล่าสุดและส่งอีเวนต์ `history` worker เปิดข้อความที่ปิดผนึกด้วย `line_open_payload()` ระหว่างสร้างแถว
4. `chat_message()` ของ UI ย้ายแชตขึ้นบนสุดและปรับจำนวนที่ยังไม่อ่าน จากนั้น `notify_unread()` แสดงการแจ้งเตือนบนเดสก์ท็อปถ้าหน้าต่างอยู่เบื้องหลัง และเล่นเสียงข้อความถ้าหน้าต่างไม่ได้ถูกใช้อยู่หรือข้อความอยู่ในแชตอื่นที่ไม่ได้เปิด แชตที่ปิดเสียงไว้จะเงียบ

## กลไกของ Linux ที่แอปพึ่งพา

Avernella พึ่งพาเคอร์เนลและ glibc แทนเฟรมเวิร์ก การรู้จักกลไกเหล่านี้ช่วยได้มากเวลามีพฤติกรรมแปลก ๆ

**โปรเซส**
- `posix_spawn` ของ `/proc/self/exe` สำหรับ worker, `pidfd_spawn` (clone3 พร้อม pidfd) สำหรับโปรแกรมเบราว์เซอร์ และ `PR_SET_PDEATHSIG` ในโปรเซสลูกทั้งสอง
- UI รอ worker ผ่าน `pidfd_open` และส่งสัญญาณถึง worker เฉพาะตอนที่ยังไม่ได้เก็บสถานะการจบ (reap) PID จึงยังไม่มีทางถูกนำไปใช้ซ้ำ
- worker จำกัดตัวเองตอนเริ่มทำงานด้วย `PR_SET_DUMPABLE`, `PR_SET_NO_NEW_PRIVS`, seccomp และ Landlock และป้องกันหน่วยความจำด้วย MDWE, `mseal()`, shadow stack, `M_PERTURB` และหน้าเฝ้าระวัง ([แซนด์บ็อกซ์ของ worker](#แซนด์บ็อกซ์ของ-worker), [การป้องกันหน่วยความจำ](#การป้องกันหน่วยความจำ))
- `posix_spawn_file_actions_addclosefrom_np` เพื่อให้โปรเซสลูกได้รับเฉพาะ descriptor ที่จำเป็น

**การรอโดยไม่ใช้ตัวจับเวลา**
- worker หลับใน `poll()` บนซ็อกเก็ต eventfd สองตัว และ `timerfd` แบบครั้งเดียว ตื่นเฉพาะเมื่อมีเหตุการณ์
- long poll แทนการตรวจเป็นระยะ การตรวจ revision สำรองทำเฉพาะตอนที่ long poll มีปัญหา
- UI รอใน `SDL_WaitEventTimeout` ตามเวลาที่เหลือถึงเฟรมหรือขั้นแอนิเมชันถัดไป และรอไม่มีกำหนดเมื่อไม่มีอะไรขยับหรือหน้าต่างถูกซ่อน

**หน่วยความจำ** ([`tune.c`](../../src/tune.c))
- `mallopt` ตั้งให้มี malloc arena สองตัว เกณฑ์ mmap 128 KiB และเกณฑ์ trim 512 KiB บัฟเฟอร์รูปขนาดใหญ่จึงคืนให้เคอร์เนลทันทีที่ปล่อย
- UI เรียก `malloc_trim` เมื่อหน้าต่างเสียโฟกัส
- ภาพย่อใช้แคชร่วม 12 MiB แอนิเมชันมีงบ 32 MiB
- รูปข้ามโปรเซสเป็น memfd ที่ปิดผนึกแทนการคัดลอก

**การจัดตารางงาน**
- การดึงและถอดรหัสรูปรันภายใต้ `SCHED_BATCH` ด้วยลำดับความสำคัญต่ำกว่า (`LINE_THREAD_BACKGROUND`)
- เธรดมีเดียของการโทรขอ timer slack ที่แคบ (`LINE_THREAD_MEDIA`) และใช้ `sched_setattr` ขอ slice ของ EEVDF ยาว 1 ms (Linux 6.12 ขึ้นไป) กับค่าขั้นต่ำของ utilization 256 จาก 1024 (uclamp) ทั้งสองอย่างยังอยู่ในคลาสการจัดตารางงานปกติและไม่ต้องใช้สิทธิ์พิเศษ บนเครื่อง 16 CPU ที่ทุก CPU ทำงานเต็ม slice นี้ลดความล่าช้าในการตื่นของตัวจับเวลาเสียงทุก 20 ms จากราว 2 ms เหลือไม่ถึง 40 µs (เปอร์เซ็นไทล์ที่ 99) เคอร์เนลที่ไม่มี uclamp จะได้แค่ slice ส่วนเคอร์เนลรุ่นเก่ากว่าจะไม่สนใจทั้งสองค่า

**เครือข่าย** ([`http_tune.c`](../../src/http_tune.c), [`udp_batch.c`](../../src/udp_batch.c))
- libcurl กับ TLS 1.2 ขึ้นไป ตรวจใบรับรองและชื่อโฮสต์ HTTP/2, TCP Fast Open และ keepalive
- มีเดียของการโทร: เธรดการโทรอ่านดาตาแกรมที่รออยู่ทั้งหมดด้วย `recvmmsg()` ครั้งเดียว และข้าม `poll()` ไปตราบที่ยังมีดาตาแกรมค้างอยู่ แพ็กเก็ตของภาพวิดีโอแต่ละภาพส่งออกด้วย `sendmmsg()` ครั้งเดียว โดยแพ็กเก็ตขนาดเท่ากันที่อยู่ติดกันรวมเป็นข้อความ `UDP_SEGMENT` (UDP GSO) ข้อความเดียว ดาตาแกรมบนสายยังเหมือนเดิมทุกประการ หากเคอร์เนลหรือตัวกรอง seccomp ปฏิเสธขั้นใด ซ็อกเก็ตนั้นจะถอยไปใช้ `sendmmsg()` แล้วจึงเป็น `sendto()`/`recvfrom()` ธรรมดา `LINE_DISABLE_UDP_BATCH=1` ปิดการรวมชุดนี้
- ดาตาแกรมที่รับมาแต่ละอันมีเวลาที่เคอร์เนลรับไว้ (`SO_TIMESTAMPNS_NEW` ไม่เช่นนั้น `SO_TIMESTAMPNS`) ซึ่ง jitter buffer บัฟเฟอร์จัดลำดับ และ REMB ใช้แทนเวลาที่เธรดการโทรอ่าน ก่อนแต่ละภาพ เธรดการโทรอ่านคิวส่งของซ็อกเก็ตด้วย `ioctl(SIOCOUTQ)` คือดาตาแกรมที่ qdisc สแตก Wi-Fi หรือไดรเวอร์ยังถืออยู่ ซึ่งเผยให้เห็นอัปลิงก์ Wi-Fi ที่อ่อนก่อนจะมีอะไรสูญหาย ([เครือข่ายที่ไม่ดี](calls.md#8-เครือข่ายที่ไม่ดี))
- ภาพถูกเข้ารหัสบนเธรดของตัวเอง (`line-encode`) ซึ่งส่งแต่ละภาพกลับผ่าน eventfd ใน `poll()` ของเธรดการโทร
- UI กับ worker อ่านจากซ็อกเก็ตครั้งละ 64 KiB คำตอบประวัติแชตขนาดใหญ่จึงใช้การอ่านไม่กี่ครั้งแทนหลายสิบครั้ง
- แคช DNS และ TLS session ใช้ร่วมกันข้ามเธรด แต่แต่ละเธรดมีพูลการเชื่อมต่อของตัวเอง
- `Retry-After` จาก HTTP 429 หรือ 503 ทำให้ RPC ทั้งหมดหยุดรอตามเวลาที่กำหนด (`line_transport_retry_after()`)

**โปรแกรมเบราว์เซอร์** ([`liff_browser.c`](../../src/liff_browser.c))
- systemd transient scope (cgroup v2 แยกของตัวเอง) ที่มี `MemoryHigh=768M`, `CPUWeight=50` และ `IOWeight=50`
- เพิ่ม `oom_score_adj` เคอร์เนลจึงเลือกเก็บคืนหน่วยความจำจากเบราว์เซอร์ก่อนไคลเอนต์ และตั้ง timer slack 1 ms ซึ่งโปรเซสของ WebKit สืบทอดไป
- web process ของ WebKit ถูกจำกัดที่ 512 MB และ network process ตัดแคชเมื่อเกิน 128 MB

## แซนด์บ็อกซ์ของ worker

worker ถือความลับทั้งหมดและแยกวิเคราะห์ทุกอย่างที่ LINE ส่งมา ทั้งคำตอบ Thrift รูป วิดีโอ และมีเดียของการโทร ช่องโหว่ใดถูกใช้โจมตีก็มักไปตกที่นี่ [`sandbox.c`](../../src/sandbox.c) จำกัด worker ตั้งแต่เริ่มทำงานก่อนจะมีเธรดใด (`line_sandbox_worker()` ซึ่ง `worker()` ใน `main.c` เรียก)

| ชั้น | เคอร์เนล | สิ่งที่กันไว้ |
| ---- | -------- | ------------ |
| `PR_SET_DUMPABLE 0` | ทุกรุ่น | โปรเซสอื่นของผู้ใช้คนเดียวกันอ่าน `/proc/<pid>/mem`, `fd` หรือ `environ`, `ptrace` โดยไม่มี `CAP_SYS_PTRACE` และ core dump ที่จะมีเซสชันติดไปด้วย |
| `PR_SET_NO_NEW_PRIVS` | 3.5 | การได้สิทธิ์เพิ่มผ่านโปรแกรม set-user-ID |
| ตัวกรอง seccomp | 3.5 (ทุกเธรดพร้อมกัน: 3.17) | การพิมพ์ใส่เทอร์มินัลที่ worker สืบทอดมา (ioctl `TIOCSTI` และ `TIOCLINUX`) การรันโปรแกรม (`execve`) namespace ใหม่ (`unshare`, `setns`, `clone` ที่มีธง namespace) การ mount, `ptrace` และ `process_vm_*`, `pidfd_getfd`, `bpf`, `perf_event_open`, `userfaultfd`, `io_uring` การโหลดโมดูลและ kexec การตั้งนาฬิกาและคำสั่งดูแลระบบอื่น ๆ และ system call ABI อื่น (i386, x32) |
| Landlock ABI 4 | 6.7 | TCP socket ที่รอรับการเชื่อมต่อ |
| Landlock ABI 6 | 6.12 | การส่งสัญญาณไปยังโปรเซสนอก worker |

ตัวกรองตอบกลับด้วย errno แทนการฆ่า worker: `EPERM` สำหรับคำสั่งที่ถูกปฏิเสธ และ `ENOSYS` สำหรับ `io_uring` กับ `clone3` ไลบรารีจึงถอยไปใช้ทางเดิมเหมือนบนเคอร์เนลรุ่นเก่า `clone3` ส่งธงผ่านหน่วยความจำซึ่ง seccomp ตรวจไม่ได้ glibc จึงหันไปใช้ `clone` ซึ่งตัวกรองตรวจธง namespace ได้

ทุกชั้นเป็นทางเลือก เคอร์เนลที่ไม่มีชั้นใด หรือแซนด์บ็อกซ์ภายนอก (Flatpak, คอนเทนเนอร์) ที่ไม่ยอมให้ใช้ชั้นใด ชั้นที่เหลือก็ยังทำงาน ไฟล์ไม่ถูกจำกัด เพราะ worker บันทึกไฟล์แนบไว้ที่ใดก็ได้ที่ผู้ใช้เลือก `LINE_DEBUG_SANDBOX=1` พิมพ์ว่าชั้นใดทำงานอยู่ในแต่ละโปรเซส เช่น `line-sandbox worker no-dump=1 no-new-privs=1 seccomp=1 landlock-net=1 landlock-signal=1 mdwe=1 seal=1(513) shadow-stack=1 memory-tagging=0 heap-wipe=1 guard-pages=1` (513 คือจำนวนช่วงที่ถูกผนึก) `LINE_DISABLE_SANDBOX=1` ไม่ใช้ชั้นใดเลย สำหรับต่อดีบักเกอร์ ถ้าใส่รายชื่อคั่นด้วยจุลภาค (`seccomp`, `landlock`, `mdwe`, `seal`, `shstk`, `mte`, `wipe`, `guard`) จะเว้นเฉพาะชั้นเหล่านั้น เช่น `LINE_DISABLE_SANDBOX=mdwe,shstk`

### การป้องกันหน่วยความจำ

Avernella เขียนด้วยภาษา C และไม่มีความสามารถใดของเคอร์เนลที่ทำให้ C ปลอดภัยด้านหน่วยความจำได้ บัฟเฟอร์ล้นหรือการใช้หน่วยความจำหลัง free ในตัวแยกวิเคราะห์ก็ยังเป็นบั๊กอยู่ดี สิ่งที่เคอร์เนลและ glibc ทำได้คือทำให้บั๊กแบบนั้นกลายเป็นโค้ดที่ผู้โจมตีสั่งรันได้ยากขึ้นมาก และจำกัดสิ่งที่โปรเซสที่ถูกเจาะจะเข้าถึงได้ [`sandbox.c`](../../src/sandbox.c) เพิ่มชั้นเหล่านี้ต่อจากการจำกัดข้างบน:

| ชั้น | ต้องมี | โปรเซส | ทำอะไร |
| ---- | ------ | ------- | ------ |
| MDWE (`PR_SET_MDWE`) | Linux 6.3 | worker และ UI เมื่อใช้ GPU จริง (Linux 6.7) | ไม่ยอมให้มีหน่วยความจำที่ทั้งเขียนได้และรันได้ หรือที่จะกลายเป็นรันได้ภายหลัง ไบต์ที่ถูกฉีดเข้ามาจึงไม่มีวันถูกรันเป็นโค้ด |
| `mseal()` | Linux 6.10, 64 บิต | worker และ UI | ผนึกโค้ด ข้อมูลอ่านอย่างเดียว และ RELRO (ซึ่งมี GOT อยู่ เพราะโปรแกรมลิงก์ด้วย `-z now`) ของโปรแกรมและของทุกไลบรารีที่โหลดตอนเริ่มทำงาน `mprotect()` ทำให้เขียนได้ไม่ได้ และ `munmap()` หรือ `mremap()` เอาอย่างอื่นมาแทนไม่ได้ |
| shadow stack ของ x86 | Linux 6.6, glibc 2.39 และ CPU ที่มี CET (Intel รุ่นที่ 11, AMD Zen 3 ขึ้นไป) | worker | CPU เก็บสำเนาที่สองของทุกที่อยู่ส่งกลับ (return address) ไว้ในที่ที่การเขียนหน่วยความจำธรรมดาเข้าไม่ถึง ที่อยู่ส่งกลับที่ถูกเขียนทับทำให้โปรเซสหยุด (`SIGSEGV`) แทนที่จะกระโดดไปที่ผู้โจมตีต้องการ |
| MTE ของ arm64 ติดแท็กฮีป | Linux 5.10, glibc 2.33 และ CPU ที่มี MTE | worker | glibc ติดแท็กให้ทุกก้อน malloc พอยน์เตอร์ที่ใช้นอกก้อนของตัวเองหรือหลัง `free()` จะเกิด fault (แบบ asynchronous) |
| ล้างฮีป (`M_PERTURB`) | glibc | worker | glibc เติม `0xff` ลงในก้อนที่คืนมา และเติมศูนย์ลงในก้อนที่แจกออกไป คำตอบและข้อความที่ free แล้วจึงไม่ค้างอยู่ และพอยน์เตอร์ที่อ่านจากหน่วยความจำที่ free แล้วจะเป็นค่าที่ใช้ไม่ได้ (non-canonical) และเกิด fault แคชรายเธรดของ glibc (ก้อนขนาดไม่เกิน 1032 ไบต์) ข้ามขั้นนี้ |
| หน้าเฝ้าระวัง (guard page) | Linux 6.13 (`MADV_GUARD_INSTALL`) ไม่เช่นนั้นใช้หน้า `PROT_NONE` | worker | คำตอบ Thrift แต่ละอันถูกถอดรหัสจากสำเนาอ่านอย่างเดียวที่ไบต์สุดท้ายชิดหน้าเฝ้าระวัง (`line_guard_copy()` ใน `transport.c`) การอ่านเลยคำตอบไปแม้ไบต์เดียว หรือการเขียนลงในคำตอบ จึงเกิด fault แทนที่จะไปแตะฮีป การ free สำเนาจะ unmap มันทิ้ง |

คอมไพเลอร์ช่วยอีกส่วนในทุกโปรเซส ได้แก่การป้องกันโฟลว์การควบคุม (`-fcf-protection=full` หรือ `-mbranch-protection=standard` บน arm64), `-ftrivial-auto-var-init=zero`, `-fstrict-flex-arrays=3` และ bounds sanitizer แบบ trap นอกเหนือจาก `_FORTIFY_SOURCE=3`, stack protector, stack-clash probe และ RELRO เต็มรูปแบบ ดู [build แบบ release ทำอะไรบ้าง](building.md#build-แบบ-release-ทำอะไรบ้าง) `make analyze` รันตัววิเคราะห์โค้ดแบบสถิตของ GCC กับซอร์สทั้งหมด

**worker ได้ shadow stack อย่างไร** glibc เปิด shadow stack ได้เฉพาะตอนโปรแกรมเริ่มทำงาน UI จึงขอให้ผ่าน `GLIBC_TUNABLES` ของ worker (`line_sandbox_tunables()` ซึ่ง `worker_environment()` ใน `ui.c` เรียก): `glibc.cpu.hwcaps=SHSTK:glibc.cpu.x86_shstk=on` glibc 2.39 ถึง 2.44 ตัด SHSTK ออกจากความสามารถของ CPU เพราะเคอร์เนลยังไม่ได้เปิดให้ตอน exec แล้วจะไม่สนใจ `x86_shstk=on` จนกว่า `hwcaps` จะระบุ SHSTK อีกครั้ง ค่าที่ใช้คือ `on` ไม่ใช่ `permissive` ไลบรารีโคเดกหลายตัวที่ libavcodec ดึงเข้ามา (libvpx, libzstd, libaom และอื่น ๆ) และไลบรารี CUDA กับ VA-API ของ NVIDIA ไม่ได้ติดเครื่องหมาย CET และ `permissive` จะปิด shadow stack เพราะไลบรารีเหล่านี้ ไลบรารีเหล่านี้ทำงานได้ถูกต้องเมื่อมี shadow stack เพราะไม่ได้สลับสแตกเอง UI ขอเฉพาะเมื่อ `/proc/cpuinfo` มี `user_shstk` และ glibc เป็นรุ่น 2.39 ขึ้นไป UI เก็บ tunable ทุกตัวที่มีอยู่แล้วใน environment ไว้ และถ้ามีตัวที่ตั้ง `x86_shstk` เองอยู่แล้ว ตัวนั้นชนะ บน arm64 ที่มี MTE UI เติม `glibc.mem.tagging=1` ในแบบเดียวกัน

**UI** UI ถอดรหัสรูปและวาดข้อความที่เชื่อถือไม่ได้ แต่ก็รันไดรเวอร์ GPU ด้วย `line_sandbox_ui_start()` ผนึกโปรแกรมและไลบรารีตอนเริ่มทำงานเป็นอย่างแรกใน `line_ui()` ก่อนจะโหลดสิ่งใดที่อาจถูกถอดออกภายหลัง เพราะ mapping ที่ผนึกแล้ว unmap ไม่ได้ `line_sandbox_ui_renderer()` เปิด MDWE เมื่อตัววาด Vulkan แบบเนทีฟทำงานบนอุปกรณ์ฮาร์ดแวร์ ไดรเวอร์ซอฟต์แวร์ของ Mesa (llvmpipe, lavapipe) คอมไพล์โค้ดด้วย LLVM และล่มภายใต้ MDWE UI จึงไม่ใช้ MDWE เมื่อตัววาดของ SDL หรืออุปกรณ์ซอฟต์แวร์เป็นผู้วาด UI ตั้งแฟล็กด้วย `PR_MDWE_NO_INHERIT` (Linux 6.7) worker และโปรแกรมเบราว์เซอร์ WebKit ซึ่ง JIT ของ JavaScript ต้องใช้โค้ดที่เขียนได้ จึงเริ่มทำงานโดยไม่มีแฟล็กนี้ บน Linux 6.3 ถึง 6.6 UI ไม่ใช้ MDWE ยังเหลือกรณีเดียว: ถ้า GPU ฮาร์ดแวร์เสียภายหลัง และ OpenGL ของหน้าต่างใหม่ถอยไปใช้ llvmpipe UI อาจล่มได้ `LINE_DISABLE_SANDBOX=mdwe` เลี่ยงกรณีนี้

UI ไม่ถูกจำกัดแบบเดียวกับ worker เพราะ UI เปิดโปรแกรมเบราว์เซอร์ WebKit ซึ่งแซนด์บ็อกซ์ของตัวเอง (bubblewrap) ต้องใช้ namespace และตัวกรอง seccomp ถ่ายทอดไปยังโปรเซสลูก

**ไดรเวอร์ที่ทดสอบแล้ว** บน Linux 7.3 กับ glibc 2.44, NVIDIA 620.73 (RTX 5050) และ Mesa 26.3 (Radeon 780M) สิ่งเหล่านี้ทำงานได้ภายใต้ MDWE: การวาดและแสดงผลด้วย Vulkan บน GPU ทั้งสองตัว (`vulkan-smoke`, `vulkan-preview --test`), OpenGL แบบฮาร์ดแวร์บนทั้งสองตัว, การถอดรหัส VP8 ผ่าน NVDEC (CUDA) และผ่าน VA-API บนทั้งสองตัว และ PipeWire เส้นทาง CUDA และ VA-API ยังทำงานได้เมื่อมี shadow stack ด้วย llvmpipe ล่มภายใต้ MDWE ตามคาด ทุกเทสต์ใน `make check` ผ่านเมื่อเปิด shadow stack, MDWE และการล้างฮีปพร้อมกันด้วย

**ต้นทุน** วัดบนเครื่องเดียวกัน การใช้ทุกชั้นของ worker ใช้เวลาราว 0.25 ms ครั้งเดียว และเวลาเริ่มทำงานของ worker ไม่เปลี่ยนอย่างวัดได้ สำเนาที่มีหน้าเฝ้าระวังใช้ราว 17 µs ต่อคำตอบขนาด 4 KiB และ 55 µs ต่อ 64 KiB เทียบกับเวลาไปกลับของเครือข่ายที่หลายสิบมิลลิวินาที การล้างฮีปทำให้การแยกวิเคราะห์และพิมพ์เอกสาร JSON ขนาด 176 KiB ด้วย json-c ช้าลงราว 4% shadow stack ไม่ทำให้ต่างอย่างวัดได้ แฟล็กคอมไพเลอร์ทำให้โปรแกรมใหญ่ขึ้น 1.3% (จาก 1,238,136 เป็น 1,254,520 ไบต์) และไม่ได้ทำให้ `render-bench` หรือเทสต์พิกเซล เสียง และ Thrift เปลี่ยนอย่างวัดได้

**สิ่งที่ไม่ได้ใช้ และเหตุผล**
- การปิดแคช malloc รายเธรดของ glibc (`glibc.malloc.tcache_count=0`) จะทำให้การล้างฮีปครอบคลุมก้อนเล็กด้วย แต่ทำให้การแยกวิเคราะห์ด้วย json-c ช้าลง 80% แคชนี้มีการปิดบังพอยน์เตอร์ (safe-linking) และการตรวจ free ซ้ำอยู่แล้ว
- `-fzero-call-used-regs=used-gpr` ลด gadget สำหรับ return-oriented programming ไปได้บ้าง แต่ทำให้โปรแกรมใหญ่ขึ้น 1% และ shadow stack ของ worker หยุดโค้ดแบบ return-oriented ที่นั่นได้อยู่แล้ว
- indirect branch tracking (IBT): ออบเจกต์มี landing pad แล้ว แต่ Linux ไม่เปิด IBT ให้โปรแกรมผู้ใช้
- MTE เขียนไว้แล้วแต่ยังไม่ได้ทดสอบ เพราะเครื่องนี้เป็น x86-64 บอร์ด Jetson ส่วนใหญ่ไม่มี MTE (Cortex-A78AE ของ Orin ไม่มี)
- รูป สติกเกอร์ และเฟรม APNG ยังถูกถอดรหัสใน UI ด้วย libpng, libjpeg-turbo และ libwebp การย้ายการถอดรหัสไปไว้ใน worker หรือในโปรแกรมช่วยที่มีตัวกรอง seccomp ของตัวเองและไม่มีอะไรอื่น จะปกป้อง UI ได้ดีที่สุด และเป็นงานใหญ่ที่สุดที่เหลืออยู่

Avernella ไม่ใช้ io_uring I/O ของ worker มีแค่ซ็อกเก็ตไม่กี่ตัวกับไฟล์เล็ก ๆ ซึ่ง `poll()` และการอ่านธรรมดาก็มีต้นทุนต่ำอยู่แล้ว และหลายระบบปิด io_uring ไว้ (`kernel.io_uring_disabled` โปรไฟล์ของคอนเทนเนอร์และ Flatpak) แซนด์บ็อกซ์ปฏิเสธ io_uring ซึ่งตัดส่วนติดต่อของเคอร์เนลนี้ออกจากมือผู้โจมตี

## สรุปเส้นแบ่งด้านความปลอดภัย

- โทเค็นและกุญแจอยู่แค่ใน worker UI ไม่เคยเห็น access token, refresh token หรือกุญแจส่วนตัว
- worker เป็นแบบ non-dumpable และทำงานภายใต้ seccomp และ Landlock ([แซนด์บ็อกซ์ของ worker](#แซนด์บ็อกซ์ของ-worker)) มีเดียไปถึง UI เป็น descriptor ที่ส่งต่อมา ไม่ใช่พาธเข้าไปใน `/proc` ของ worker
- บั๊กหน่วยความจำถูกใช้โจมตีได้ยากขึ้น: ไม่มีหน่วยความจำที่ทั้งเขียนได้และรันได้ โค้ดและ GOT ถูกผนึก worker มี shadow stack ก้อนฮีปถูกล้าง และมีหน้าเฝ้าระวังต่อท้ายคำตอบจาก LINE ([การป้องกันหน่วยความจำ](#การป้องกันหน่วยความจำ)) ทั้งหมดนี้ไม่ได้ทำให้โค้ด C ปลอดภัยด้านหน่วยความจำ
- เธรดการโทรได้เฉพาะข้อมูลของสายนั้น ไม่เคยได้โทเค็นของบัญชี
- โปรแกรมเบราว์เซอร์ได้รับโทเค็นของแอป LINE ผ่านซ็อกเก็ตเท่านั้น ไม่ผ่านอาร์กิวเมนต์หรือตัวแปรสภาพแวดล้อม และไม่ถูกบันทึกลง log
- การดาวน์โหลดรูปจากโฮสต์ใดก็ได้ (Flex, rich message) ทำแบบไม่ระบุตัวตน ใช้ HTTPS เท่านั้น และปฏิเสธที่อยู่ในเครือข่ายส่วนตัวและเครือข่ายในเครื่อง ([`flex_asset.c`](../../src/flex_asset.c))
- อินพุตทุกอย่างจาก LINE ถูกตรวจขนาดและชนิดก่อนใช้: ตัวถอดรหัส Thrift จำกัดการซ้อนไว้ 48 ชั้นและค่าทั้งหมด 300,000 ค่า ฟังก์ชันอ่านฟิลด์ตรวจชนิดของ JSON
- ไฟล์เซสชันเป็นข้อความธรรมดาที่ป้องกันด้วยสิทธิ์ของไฟล์ ใครที่อ่านไฟล์นี้ได้ก็สวมรอยเป็นอุปกรณ์ที่เชื่อมนี้ได้ Avernella ไม่ได้ใช้ keyring ของเดสก์ท็อป (Secret Service) กับไฟล์นี้ เพราะต้องมี keyring ทำงานอยู่ ซึ่งระบบที่ไม่มีหน้าจอมักไม่มี และกุญแจที่เก็บไว้ข้างไฟล์ก็ไม่ได้ช่วยอะไร
- โทเค็น บรรทัด header ที่มีโทเค็น และเนื้อหาคำตอบ HTTP ถูกล้างก่อนคืนหน่วยความจำ json-c คืนหน่วยความจำของสตริงกุญแจ Letter Sealing ใน `s->keys` โดยไม่ล้าง และ libcurl กับ OpenSSL ก็เก็บสำเนาชั่วคราวของสิ่งที่ส่งและรับไว้เอง
