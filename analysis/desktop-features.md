## Implementation evidence

In the supplied LINE 26.16.0 Android package, the DEX methods `classes12.dex Lh36/b;->invoke` and `classes3.dex Liz6/c;->invoke` identify lookup by LINE ID or personal ticket and by phone. `classes3.dex Llf3/e2;->invoke` identifies the friend-add operation. The C client preserves the original lookup method when sending the addition. The service returns the account identity before the desktop offers the add button. The companion protocol reference also documents the separate favorite, visibility and display-name operations. [Relation service reference](https://github.com/softnetics/line-rs/blob/addf69c2e886a2364a396ce360093a62119dcb32/src/service/relation.rs)

The shipped `classes5.dex Lvq8/a;->C` contains both Letter Sealing message formats. Regression fixtures cover legacy CBC with MAC verification, current GCM and exact-generation contact key lookup. A virtual desktop test rendered decrypted text for both formats through the normal worker path. [LINE Encryption Overview](https://www.lycorp.co.jp/en/privacy-security/line-encryption-whitepaper-ver2.2.pdf)

The profile and friend-request work reads the same APK. OpType values come from the enum in `classes7.dex Lts8/ce;`: 1 UPDATE_PROFILE, 2 NOTIFIED_UPDATE_PROFILE, 4 ADD_CONTACT, 5 NOTIFIED_ADD_CONTACT, 6/7 BLOCK and UNBLOCK_CONTACT, 49 UPDATE_CONTACT, 63 FRIEND_REQUEST_ACCEPTED, 78 NOTIFIED_BUDDY_UPDATE_PROFILE, 88 NOTIFIED_FRIEND_REQUEST and 141 NOTIFIED_UPDATE_PROFILE_CONTENT. `classes5.dex Lts8/de;` gives the Operation fields, with param1 at field 10. `classes3.dex Lbf7/o6;` is the V3 TargetProfileDetail, whose statusMessage (4) is `Lts8/lg;` with the text in field 1. `Lts8/g7;` is the legacy Contact, with statusMessage at 26. `getFriendRequests_args` is direction (1, INCOMING = 1) and lastSeenSeqId (2). Each FriendRequest (`Lts8/x9;`) carries eMid, mid, direction, method, param, timestamp, seqId, displayName and picturePath. `removeFriendRequest_args` is direction and midOrEMid. Adds from a group, a stranger's message or a friend request use the groupMemberList (5), strangerMessage (13) and friendRequest (21) arms of the `Lbf7/e;` tracking union. Rich messages are ContentType RICH (17) in `classes7.dex Lts8/q7;`. The metadata keys DOWNLOAD_URL, SPEC_REV, ALT_TEXT and MARKUP_JSON, with `RICH_` aliases, appear in `classes.dex Lpn8/b$c;`. The kotlinx-serialization descriptors in `classes5.dex Luo8/a$*` give the markup: RichMessage (canvas, expireAt, images, actions, scenes), Canvas (width, height, initialScene), Image (x, y, w, h, imageUrl), Scene (draws, listeners, video), Draw (x, y, w, h, image) and Video (x, y, w, h, videoUri, previewUri, button). A Listener is action, type (touch) and params. An Action is type, text and params, with params for web (linkUri, httpUri), postback (linkUri), sendMessage (text), clipboard (clipboardText), transition (nextScene) and app. The profile picture upload uses OBS `talk/p/<mid>`, as in the existing message-media OBS client and the open-source LINE clients.

## Verification

The user confirmed text messaging with a paired personal account. The friend, group and read-receipt tests use synthetic accounts. They exercise real Compact Thrift encoding, worker request handling and native UI interactions without modifying a live account. LINE can decline friend search because of privacy settings, age verification, regional restrictions or account limits. The client displays the service error. [Friend search conditions](https://help.line.me/line/desktop/?contentId=200000585&lang=en)
