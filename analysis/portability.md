# LINE 26.16.0 Android build

The supplied APKM contains LINE for Android, package `jp.naver.line.android`, version code `261600106`. Its SHA-256 is `4a82c3173a935c52dbe96b8768b73a2dda7284b860f37e4982d72b5672dbf1af`. The observations below apply to these bytes.

| Question | Static evidence | Consequence for a native Linux client |
| --- | --- | --- |
| What can be executed? | The base APK contains 14 DEX 039 files. Each of two ABI splits contains 73 ELF shared libraries. Their ELF headers identify all 73 as AArch64 in one split and ARM32 in the other. The other six splits contain density resources. | The bundle supplies Android bytecode and ARM libraries. An x86-64 Linux build needs its own executable and desktop UI. |
| How does it start? | The binary manifest specifies API 32 minimum, API 36 target, and required ABI and density splits. The default enabled MAIN/LAUNCHER activity is `jp.naver.line.android.activity.SplashActivity`. In `classes.dex`, `LineApplication` extends `android.app.Application`. | Android starts the app through its activity and application lifecycles. The Linux entry point must provide its own lifecycle. |
| How is a message submitted? | In `classes7.dex`, `TalkServiceClientImpl` extends `LegacyTalkServiceClientImpl`. In the latter's method `M2`, DEX code item `0x413794`, the instructions construct an argument struct, load the literal `sendMessage` at byte offset `+0x4e`, and pass it to an Apache Thrift method at `+0x52`. The method also selects a `recv_sendMessage` result handler. | A native implementation can serialize this RPC. A working send also depends on server authorization, the message envelope, compatible keys and acknowledgment handling. |
| Which Android facilities are coupled to chat? | The manifest declares `ChatHistoryActivity` and `LineFirebaseMessagingService`. The latter subscribes to `com.google.firebase.MESSAGING_EVENT` and extends Google's messaging service in `classes5.dex`. `SecondaryDeviceLoginActivity.onCreate` in `classes14.dex` invokes an AndroidX fragment lifecycle method and obtains a dependency via Android Context. | The chat UI, incoming-message notification delivery and device-linking UI need Linux implementations. |
| What indicates Letter Sealing support? | The manifest declares E2EE key-exchange confirmation and chat fingerprint activities. In `classes5.dex`, method `Lvq8/a;->C`, code item `0x5ac3b0`, writes `e2eeVersion` into a map at `+0x50c` and `+0x510`. `classes3.dex` defines v1 and v2 `LetterSealingKey` models. | Text transport and device identity are separate from rendering chat history. These observations establish protocol-related components. The field layout and cryptographic algorithms require independent evidence. |
| Can the Android native libraries be linked directly? | `readelf -d` finds dependencies on Android's `liblog.so` and `libcrypto3line.so` in the AArch64 `liblegy.so`. `libmm.so` needs Android system and JNI graphics libraries. `libsurface_util_jni.so` imports `ANativeWindow_fromSurface` and exports a Java camera JNI entry point. | Even on ARM Linux, CPU compatibility alone does not satisfy these dynamic dependencies. |

## Native text interoperability

The Android bytecode corroborates four RPC names used by the C implementation. In `classes7.dex`, methods `g`, `h`, `i` and `o` of `Lts8/wh;` pass `getE2EEGroupSharedKey`, `getE2EEPublicKey`, `getLastE2EEGroupSharedKey` and `negotiateE2EEPublicKey` respectively to the Apache Thrift client. Their code item offsets are `0x5aca90`, `0x5acc8c`, `0x5acb10` and `0x5acc18`. In `classes14.dex`, `Lp95/w0;->invoke` at `0x4a19e4` reads and Base64-decodes three named fields from a map, `encryptedKeyChain`, `publicKey` and `hashKeyChain`.

For the native client, the cryptographic design comes from LINE's public description, and the detailed message and pairing formats were cross-checked against LINEJS's interoperability implementation. [LINE encryption whitepaper](https://scdn.line-apps.com/stf/linecorp/en/csr/line-encryption-whitepaper-ver2.1.pdf) · [LINEJS Letter Sealing source](https://github.com/evex-dev/linejs/blob/119b0c7e03685de6be95737560521f81f1d620ce/packages/linejs/base/e2ee/mod.ts) · [LINEJS wire definitions](https://github.com/evex-dev/linejs/blob/119b0c7e03685de6be95737560521f81f1d620ce/resources/line/line.thrift)

[The C fixtures](../tests/sealing.c) use synthetic account and peer keys. They exercise keychain verification, direct messages to two key generations, group messages from two senders, outgoing encryption, mismatched key IDs and authentication failures. They establish offline compatibility with those wire fixtures. The user subsequently paired their Linux session and confirmed live text delivery.

### Sender key rejection in LINE 26.19.0

In the Android 26.19.0 base APK (SHA-256 `5234750455cf0757edcc9de5c1d4e05ed7c5ee1a82405225fae99455e2adefe6`), `jm8.l9` maps 83 to `E2EE_UPDATE_SENDER_KEY` and 84 to `E2EE_UPDATE_RECEIVER_KEY`. The code-83 branch in `lh8.k.c` and `l41.a.d` clears the active identity from memory and invokes the local key registration path. `lh8.h0.c` exits before generating a key when `qa0.e0.h` identifies the device as secondary. The recipient-key branch instead clears the chat's cached peer key information. Avernella gets its own private keychain through phone-approved pairing and handles the rejection without resending the message or changing the session.

## Video call negotiation and recorded clips

The ARM64 split contains `libandromeda.so` (SHA-256 `27bed6d41ad1ba14b7f81dc2ad197b4872261e5a3842c3457f3a9e69bb32f8db`). REA 6.9.0 `inspect-native-exports` identifies its ELF exports in record `ev_c3a9a101a96576333422bb07c50b42aeb7aa880bf669af17234fae6327da111f`. A bounded AArch64 disassembly of `vns_video_packer_create`, addresses `0x7f1b0c` to `0x7f1be4`, shows independent branches to standard and EVS3 video packetizers. For example, the branches at `0x7f1b44` and `0x7f1b58` select different VP8 packetizers. At the factory entry, format argument `w4=3` selects standard AVC for codec `w2=3` and standard VP8 for `w2=2` or `10`. Formats `w4=1` and `2` select EVS3 AVC for `w2=3`, EVS3 VP8 for `w2=10`, and EVS3 SVC for `w2=4..6`. The disabled video offer alone does not establish both arguments. In `ampCallVideoStart`, the program calls `ampLibCallVideoSetStream` at `0x491320` and `ampLibCallVideoSendUpdate` at `0x491518`. These are static call sites.

The packetizer builder at `0x7eeb30` chooses the standard RTP VP8 format in NonPlanet mode. The Planet branch selects EVS3. Huygens maps `normal-video` (profile 2) to the `evs3` codec string at `0xa1910c`, and the codec lookup at `0x8a4db8` maps that string to codec 10, EVS3 VP8. The Linux client advertises the base VP8 profile and declines other selected profiles. It reads the signaled sender and receiver SSRCs from the answer. The VP8 packetizer and depacketizer were exercised on synthetic input, separately from the local encrypted media tests. [PLANET call schema](https://github.com/evex-dev/linejs/blob/v3.6.5/packages/linejs/client/features/call/planet/schema.ts) · [LINE Planet codec documentation](https://docs.lineplanet.me/overview/specification/call-quality)

Android `classes5.dex Ldq8/f;-><clinit>` at `0x1e676c` maps `CV` to incoming video. In the same DEX file, `Lts8/w9;-><clinit>` at `0x4894a0` assigns video route type 2. The Java client selects audio plus video and lets the native library choose the packet profile. The Linux port uses the documented VIDEO domain for its media keys. Local fixtures exercise incoming and outgoing negotiation, bidirectional SRTP video and Opus audio, and rejection of tampered or replayed media. Android and Windows/Mac interoperation still needs a two-account trial. [LINE encryption overview](https://www.lycorp.co.jp/en/privacy-security/line-encryption-whitepaper-ver2.2.pdf)

For camera clips, the native app opens the Linux camera and microphone only for the recording action. The recorder uses FFmpeg to create an H.264/AAC MP4 that goes through the encrypted video attachment path after user confirmation. [Recorder tests](../tests/video_record.c) use a generated picture and tone, verify both recorded tracks with ffprobe, and check cancellation and private-file cleanup.

## Custom LINE emoji

The Android 26.16.0 package distinguishes modern shop emoji (sticons) from ordinary Unicode characters. In `classes2.dex`, `Luq5/g;-><clinit>` maps the STICON shop type to `sticonshop` at code item `0x574664`. In `classes3.dex`, `Luh7/g;->h` constructs the locale and requests 100 shop summaries per page at code item `0x5d9414`. The wrapper at `classes7.dex:Ljp/naver/line/android/thrift/client/impl/e2;->f2`, code item `0x414784`, dispatches `getOwnedProductSummaries`. The Linux client reads account-owned summaries from this shop using Compact Thrift and obtains each pack's actual ordered item IDs and labels from LINE's public product manifest. The account-specific branch has synthetic protocol fixtures. A real account with purchased emoji is needed to verify how its present-day shop returns those entitlements. [Shop service path and methods](https://github.com/evex-dev/linejs/blob/v3.6.5/packages/linejs/base/service/shop/mod.ts)

For the offline picker index, the 45 product identifiers in LINE's published emoji list were matched to English LINE STORE product names, zero prices and versioned pack image URLs on November 19, 2026. Each Android pack manifest listed contiguous item IDs beginning at 001. The complete manifests contained 9,175 items across those products, including 211 in LINE Basic Emoji. The source contains the product IDs, names, versions and item counts. The client fetches alternate-text labels and artwork from LINE on demand and pages the results. The shop can apply regional availability and account-specific entitlement rules. [LINE's public emoji list](https://developers.line.biz/en/docs/messaging-api/emoji-list/) · [LINE Basic Emoji store listing](https://store.line.me/emojishop/product/670e0cce840a8236ddd4ee4c/en) · [Example ordered manifest](https://stickershop.line-scdn.net/sticonshop/v1/product/670e0cce840a8236ddd4ee4c/android/meta.json)

Public GETs for Animated BROWN and Animated LINE FRIENDS minini returned APNG images from the Android sticon CDN using the `_animation.png` suffix. Each contained an `acTL` animation chunk at byte 37. The corresponding unsuffixed PNGs contained the still poster. The download policy validates product and item identifiers, uses this single HTTPS origin and requests the still poster when the animation is missing (HTTP 404). [Animated BROWN listing](https://store.line.me/emojishop/product/612762fee63ed0172f7c3660/en) · [Animated minini listing](https://store.line.me/emojishop/product/62a6fb695658444ccadfba61/en) · [Emoji catalog and asset fixtures](../tests/emoji.c)

## Named groups and invitations

In `classes.dex:Lwf3/e;->d`, code item `0x526e60`, the Android creator selects GROUP or ROOM, builds a request from the next sequence number, selected type and target MID set, and sets its name. `classes5.dex:Lwf3/h0;->invoke` dispatches that request as `createChat` at code item `0x5b0814`. Compact Thrift defines GROUP as 0 and ROOM as 1. The native client creates GROUP conversations and reads their type before offering explicit invitations to existing friends. Member and pending-invitee lists come from separate maps in the group extra fields. Incoming invitations are independently listed through `getAllChatMids` with the invited-chats flag. Accept and reject call distinct TalkService methods. [LINE group behavior](https://help.line.me/line/smartphone/?contentId=20008159&lang=en) · [TalkService definitions](https://github.com/evex-dev/linejs/blob/v3.6.5/resources/line/line.thrift)

[Group fixtures](../tests/groups.c) exercise creation, invite preflight, member and pending lists, acceptance, rejection and validation. On an isolated Xvfb display with synthetic contacts, the app opened a newly created group, invited a second friend from another roster page and responded to two invitations from groups outside the existing chat list. Reading the roster, editing a name, selecting friends and opening invitation details each issued zero mutations. Live LINE acceptance and account entitlement remain service checks.
